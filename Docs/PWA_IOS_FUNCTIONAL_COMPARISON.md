# Сравнение функций PWA и iOS

Дата: 21 сентября 2026.  
iOS: App Store **1.0.3**, Build **9**.  
PWA: аудит от 21 сентября 2026 (`Docs/PWA_FUNCTIONS_AUDIT.md`).

Цель документа — понять паритет сценариев, а не копировать веб-архитектуру. Сервер PWA (NestJS, Prisma, PostgreSQL, ЮKassa, JWT) **нельзя** переносить в iOS. iOS остаётся полностью локальным приложением.

## Как читать таблицу

| Колонка | Смысл |
| --- | --- |
| PWA / iOS | Кратко, есть ли сценарий |
| Состояние в iOS | Есть / Частично / Нет / Сильнее / Слабее |
| Влияние на данные | Нет / Только UI / Новые необязательные поля / Миграция / Риск 1.0.3 |
| Рекомендация | Оставить / Улучшить / Добавить / Отложить / Не переносить |

Подписки, тарифы, StoreKit, USER/PRO, trial, restore и DEMO **не предлагаются к изменению**. Если функция их касается — рекомендация всегда «отложить».

## 1. Реализовано в обоих приложениях

Рабочий контур частной стройки совпадает по смыслу:

- список и карточка проекта;
- создание объекта с пятью осями конструктива;
- 11 макроэтапов с плановыми и фактическими датами;
- рабочие чек-листы по типу конструкции, заметка, фото пункта, справка;
- бюджет план/факт и журнал расходов;
- глобальная лента фото и файлы объекта (включая основной PDF);
- контакты объекта с избранным и звонком;
- глобальные задачи и календарь;
- калькуляторы бетона, арматуры, доски, блоков, штукатурки, шпаклёвки, утеплителя;
- CSV и PDF по расходам, PDF «для заказчика»;
- фильтры списка проектов (все / текущие / завершённые).

Это уже закрытые сценарии. Их не нужно «портировать из PWA». Нужно сохранять поведение iOS 1.0.3.

## 2. Лучше реализовано в iOS

- **Офлайн.** iOS — локальное приложение. PWA без кэша не работает без сети.
- **Расходы.** Полный CRUD; в PWA расход нельзя исправить или удалить.
- **Плановый бюджет.** Поля этапов, а не JSON-строка в одном поле проекта.
- **Напоминания задач.** Локальные уведомления реально ставятся; в PWA push выключен флагами.
- **Смена конструктива после создания.** В PWA оси заблокированы. В iOS пикеры вызывают `updateProjectMeta` (это удобно, хотя смена пака рискованна для merge по title).
- **Причины просрочки.** Enum + комментарий вместо свободного текста.
- **Поиск проектов** и сортировки, включая ручной порядок.
- **Задачи с дашборда**, без пустого маршрута `/tasks` проекта.
- **Полевая скорость чек-листа:** отметить все пункты, сбросить прогресс этапа, удалить все фото этапа.
- **Фото без серверного лимита 9 МиБ / HEIC-конвейера.**
- **iPhone-native UI** (не веб-колонка 430px).

## 3. Лучше реализовано в PWA

- **Лист замечаний** («Внимание · N») со списком пунктов `NEEDS_ATTENTION` и переходом к пункту.
- **Три рабочих статуса пункта в основном UI**, включая «нужно внимание».
- **PDF именно по рабочим чек-листам** (хаб, прогресс блоков, замечания до 80).
- **Отдельный PDF бюджета** (план JSON + фактические расходы).
- **График долей расходов.**
- **Поиск по контактам.**
- **Трёхшаговый мастер создания** с явной проверкой перед записью.
- **Публичные legal-страницы и лендинг** (для сайта, не для native-паритета).

## 4. Есть в PWA, но отсутствует в iOS

Продуктовые пробелы iOS (без подписок и DEMO):

| Пробел | Комментарий |
| --- | --- |
| Лист замечаний по объекту | Самый заметный UX-разрыв |
| Статус «Проблема» в `ChecklistItemRow2` | Поле есть, рабочий путь его не ставит |
| PDF рабочих чек-листов (ProgressStore) | Текущий PDF читает таймлайн `project.stages` |
| Отдельный PDF «бюджет план+факт» | Экран бюджета есть, файла отчёта нет |
| График структуры расходов | Только таблицы/фильтры |
| Поиск в записной книжке контактов | Список только сортируется |
| Тип стен «Каркас» | Нет значения в `WallType` |
| Мастер из трёх шагов | Иной UX, не отсутствие создания |
| mailto «идея / заказ строительства» | Профильные мелочи сайта |
| Облачный бэкап аккаунта | Это сервер PWA, не функция native |

Не считать пробелом iOS: регистрацию на сервере, сброс пароля, ЮKassa, Web Push, service worker, админку, лендинг.

## 5. Есть в iOS, но отсутствует в PWA

- Правка и удаление расхода.
- Локальная работа без сети.
- Локальные push/напоминания задач, которые включены в продукте.
- Смена типа фундамента/стен/крыши после создания.
- Структурированная причина задержки.
- Поиск по списку проектов.
- Меню массовых действий на этапе (все выполнены / сброс / удалить фото).
- Экспорт PDF расходов и клиентского PDF уже в бюджете iOS (в PWA клиентский PDF тоже есть; edit расходов — нет).
- Настоящие StoreKit-покупки и restore (в PWA restore — заглушка). **Не сравнивать дальше: подписки отложены.**
- Полноценный DEMO внутри приложения. **Не трогать.**

## 6. Реализовано частично

- **Статусы пункта.** Модель iOS трёхзначная, UI рабочего чек-листа двузначный.
- **PDF «по чек-листам».** Файл есть, но источник данных — таймлайн, не рабочие паки.
- **Прогресс %.** Считается, но формулы на разных экранах iOS расходятся (двери не входят в среднее списка/дашборда).
- **iPad.** Приложение запускается, отдельного iPad-layout почти нет.
- **Поиск.** Есть у проектов, расходов, задач; нет у контактов и пунктов чек-листа.
- **Уведомления.** iOS — локальные по задачам; центра уведомлений как в PWA нет (и PWA сам выключен флагами).
- **Резервное копирование.** У PWA это сервер; у iOS нет пользовательского backup/restore.
- **Навигация бюджета на iPad** слегка адаптивна, остальное — iPhone.

## 7. Не следует переносить в iOS

- Бэкенд, Prisma-схему, JWT/cookie, BFF.
- ЮKassa, trial без карты, checkout-return, выбор `userEditableProjectIds` как веб-модалку.
- `sessionStorage` DEMO и cookie `bc_demo_session`.
- Service worker, Web Push, badge, «сеть или ничего».
- Хрупкий `budgetSummary` JSON вместо полей iOS.
- Блокировку конструктива после создания — это ухудшит iOS, где пикеры уже есть.
- Админку оператора и `/admin` каркас.
- Product analytics API как обязательную подсистему.
- Совместный доступ, роли на объекте, мультивалютность, НДС, импорт «как в Excel» без отдельного проекта.
- Автоматический перенос React-экранов, pdfmake, pdf.js, URL-маршрутов.

## 8. Может угрожать совместимости существующих данных

Любое из перечисленного **запрещено без отдельного согласования**:

- удаление/переименование полей `Project`, `Stage`, `StageItem`, расходов, задач, контактов;
- смена `rawValue` у `ItemStatus`, типов конструктива, `DelayReason`, категорий расходов;
- миграции JSON в Documents;
- склейка ProgressStore обратно в `Project.stages`;
- переименование `title` пунктов в JSON-паках (merge прогресса по строке);
- новая обязательная ось конструктива или обязательное поле без `decodeIfPresent`;
- смена формул прогресса так, что «50%» у пользователя 1.0.3 станет другим числом без объяснения;
- отдельное хранилище замечаний вместо существующего `ItemStatus.issue`;
- копирование PWA-модели бюджета-строки поверх полей план/факт iOS.

Безопасные улучшения этого этапа опираются на **уже существующие** поля и файлы.

## 9. Затрагивает подписки или DEMO и поэтому откладывается

Не анализировать способы изменения. Только фиксация:

- тарифы USER/PRO, лимит 2 проекта, paywall, StoreKit, restore, trial;
- любой экран, который меняет `isReadOnlyMode` / выбор редактируемых проектов;
- DEMO: вход, префилл, баннеры, coachmark, запись на диск, переход DEMO → обычный проект;
- уведомления, если потребуется менять DEMO-флаги или префилл задач;
- «онбординг как в PWA /try-demo»;
- удаление аккаунта с возвратом в DEMO;
- аналитика, завязанная на тариф.

Если при проектировании листа замечаний понадобится менять префилл DEMO (сейчас часть пунктов DEMO уже со статусом `issue`) — **не менять префилл**. Только показать уже сохранённый статус.

iOS 1.0.3 уже закрывает основной контур PWA и в нескольких местах сильнее (офлайн, CRUD расходов, уведомления задач, нормальный бюджет).

Самый честный продуктовый разрыв: **цикл замечаний** (поставить «проблема», увидеть список, выгрузить в PDF рабочих чек-листов). Это не требует новой модели данных.

Второй разрыв: **отчёты берут не те данные** (таймлайн вместо ProgressStore).

Третий, меньший: **поиск контактов** и **PDF сводки бюджета**.
