# Правила разработки BuildChecklists iOS

Это рабочий регламент репозитория. Нарушать его «ради скорости» нельзя: эта папка — источник истины для iOS и эталон для Android.

Актуально для релиза **1.0.3 / Build 9**.

---

## Порядок работы над любой задачей

1. **Анализ.** Прочитать затронутые файлы и связанные документы в `Docs/`. Понять, какой контур данных меняется: `Project.stages`, ProgressStore, расходы, подписка или DEMO.
2. **План.** Кратко зафиксировать: что меняется, что не меняется, как проверить. Если задача ломает формат JSON, подписки или DEMO — остановиться и согласовать.
3. **Только потом изменения.** Не начинать с рефакторинга «заодно».
4. **Проверка.** Пройти затронутый пользовательский сценарий. Для UI — не ограничиваться одним экраном: список проектов, дашборд, сроки, бюджет, фото должны остаться согласованными.
5. **Документация.** Если изменилось поведение, обновить соответствующий файл в `Docs/` в той же задаче, не «потом».

Нет анализа — нет права менять код.

---

## Что считать крупной задачей

Крупная задача — любая из:

- новый этап строительства или новый тип конструкции;
- изменение ProgressStore / merge по title;
- изменение формата `Project`, `ExpenseItem`, `Stage`;
- DEMO;
- подписки и роли;
- миграция данных на диске;
- «навести порядок» в AppStore / MainTabView.

Перед крупной задачей нужна **резервная точка**:

- git stash / коммит (коммит — только если пользователь явно попросил, иначе как минимум сообщить, что этап закрыт и коммит рекомендуется);
- понимание, как откатиться;
- не смешивать в одной сессии рефакторинг и продуктовую правку.

После завершения большого этапа **рекомендовать Git commit**. Самостоятельно коммитить только по прямой просьбе пользователя.

## Архитектура

- Не менять архитектуру без необходимости.
- Не вводить второй глобальный store «на время».
- Не складывать рабочие чек-листы обратно в `Project.stages` через `materialize`.
- Не тащить сетевой бэкенд и не оживлять комментарии про Supabase.
- `LoginView` не подключать «за компанию», пока не поставлена отдельная задача на вход.
- `SeedPackLoader` и пустой `SeedsPacks` не использовать как место для новых паков: новые паки — в `Resources/Seeds/<Stage>Packs`.

Два контура (таймлайн vs ProgressStore) — принятая данность. Унификация — отдельный проект, не побочный эффект бага.

---

## Данные и совместимость

- Не ломать уже лежащие в Documents JSON. Новые поля — optional + default в `decodeIfPresent`.
- Не переименовывать `title` этапов и пунктов в JSON-паках: ProgressStore мержит по title.
- Не менять `rawValue` enum’ов (`FoundationType`, `ExpenseCategory`, `GlobalStageCategory`, `ItemStatus`, …) без миграции.
- Не менять имена файлов persist: `build_checklists_projects.json` и остальные.
- Не менять ключи UserDefaults без задачи на миграцию ключа.
- Не менять Product ID подписок.
- Абсолютные пути медиа уже хрупкие (`existingFileURL`). Не переходить на новые папки, не оставив поиск в старых (`BCPhotos`, `BCDocs`, `BC_Media`).

Прогресс пользователя ценнее «красивой» модели.

---

## ProgressStore

- Не менять ProgressStore без анализа всех читателей: список проектов, дашборд, бюджет, глобальные фото, DEMO-префилл, зачистка DEMO.
- File-store и UserDefaults-store (двери, кровля) ведут себя по-разному. Новый этап копировать с ближайшего аналога, не «с первого попавшегося».
- `load(projectID:typeID:)` и простой `load(projectID:)` — разные методы. Дашборд часто берёт простой load без merge.
- `overallProgress` сейчас **не включает двери**. Менять формулу — менять все копии (список, дашборд, бюджет) одним решением.
- Сохранение с экрана стадии + `bcProgressDidChange` — обязательная пара. Забыли нотификацию — карточка проекта врёт, пока пользователь не переоткроет экран.

---

## DEMO

- Не включать DEMO в `bootstrap`.
- Не сохранять роль `.demo` в UserDefaults.
- Не включать persist JSON «чтобы демо было удобнее».
- Префилл проекта, таймлайна, ProgressStore, расходов, плана и фото менять комплектом.
- Расширяя DEMO, расширять и `removeDemoProgressArtifacts` на все реально пишущиеся папки.
- Подробности: `DEMO_MODE.md`.

---

## Подписки и доступ

- USER = 2 проекта, PRO = без лимита, нет entitlements + не DEMO = read-only.
- Любая новая кнопка записи должна уважать `ensureCanMutate` / `isReadOnlyMode`.
- Не выдавать PRO локально «для проверки» в релизе.
- Restore только через `StoreKit.AppStore.sync()`.
- Подробности: `SUBSCRIPTIONS.md`.

---

## UI и файлы-гиганты

- `Store/AppStore.swift` и `Views/Main/MainTabView.swift` трогать минимальным диффом.
- Не разносить файл «на модули» без отдельной задачи.
- Новый экран стадии копировать паттерн существующего (`FoundationStagesScreen` + `StageDetailView2` + `ChecklistItemRow2`), не `StageDetailView` + `ItemCardView`.
- Не дублировать `overallProgress` третьей копией с другой формулой.

---

## Рефакторинг

Запрещены неожиданные рефакторинги:

- переименование слоёв и папок;
- перевод на SwiftData / TCA / свой Redux;
- массовый reformat;
- удаление «мёртвого» кода (`LoginView`, `StageDetailView`, дубли `Resources/FoundationPacks`, `SeedPackLoader`) без явной задачи — у этого кода есть исторический смысл и риск задеть pbxproj;
- смена языка интерфейса;
- генерация UUID пунктов заново при каждом открытии экрана.

Рефакторинг допустим, только если он и есть задача, с планом совместимости данных.

---

## Коммиты и копии проекта

- Коммит — по просьбе пользователя.
- После большого этапа напомнить: «можно зафиксировать git commit».
- Не пушить, не force-push, не править git config.
- Не разрабатывать в папках BuildChecklists 2 и 3.

---

## Как проверять

Минимум после продуктового изменения:

1. Холодный старт без DEMO — Welcome, не учебный проект.
2. DEMO — объект на месте, % ненулевой, фото, расходы, бюджет, подсказки.
3. Kill приложения — DEMO пропал, боевые JSON не перезаписаны учебным объектом.
4. Если трогали чек-листы — открыть стадию, отметить пункт, вернуться на список: % обновился.
5. Если трогали доступ — USER лимит, PRO без лимита, read-only блокирует запись.

Нет проверки — задача не закончена.
