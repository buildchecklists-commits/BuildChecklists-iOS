# Предложения для следующего релиза iOS

Дата: 21 сентября 2026.  
База: iOS 1.0.3 (Build 9).  
Сравнение: `Docs/PWA_IOS_FUNCTIONAL_COMPARISON.md`.  
PWA: только сценарии из `Docs/PWA_FUNCTIONS_AUDIT.md`.

Подписки и DEMO в этот релиз не входят. Предложения, которые могут их задеть, отнесены в категорию D.

---

## Состав ближайшего релиза (рекомендация)

Четыре улучшения, все из категории A:

1. **Статус «Проблема» в рабочей строке чек-листа**
2. **Лист замечаний на дашборде объекта**
3. **PDF-отчёт по рабочим чек-листам (ProgressStore)**
4. **Поиск по контактам проекта**

Запасной пятый пункт того же релиза, если останется ёмкость: **фильтр «только проблемы» на экране этапа** (часть того же цикла замечаний, тоже категория A).

Не включать в ближайший релиз: график расходов, мастер создания, тип стен «Каркас», iPad-layout, backup/restore, унификацию формул %, облако, подписки, DEMO.

Почему этот набор:

- заметная польза на объекте (замечания — главный разрыв с PWA);
- нет миграции и новых сущностей;
- не трогает StoreKit и DEMO-префилл;
- каждый пункт можно проверить отдельно на копии проекта 1.0.3;
- PDF и поиск контактов не зависят друг от друга и могут идти после замечаний.

---

## Последовательность реализации (когда будет разрешено писать код)

1. Спроектировать UX трёх статусов в `ChecklistItemRow2` (не ломая простой тап «готово»).
2. Включить постановку/снятие `ItemStatus.issue` в рабочем пути.
3. Собрать лист замечаний на дашборде из ProgressStore.
4. Добавить фильтр на экране этапа (по желанию в том же PR, что и лист).
5. Сделать PDF, который читает ProgressStore и включает замечания.
6. Добавить поиск контактов — независимый маленький шаг.

Первой на детальное проектирование взять **функцию 2 в связке с функцией 1**: лист замечаний бессмысленен, пока рабочая строка не умеет ставить «Проблема». Проектировать их как один продуктовый цикл.

# A. Безопасные

Не меняют существующую модель данных и не требуют миграции. Читают или показывают уже сохранённые поля.

---

### A1. Статус «Проблема» в рабочей строке чек-листа

**Проблема пользователя.** На объекте нельзя пометить пункт как проблему в основном экране этапа. Есть только «сделано / не сделано». Старые экраны с «Проблема» не используются рабочим путём (`ChecklistItemRow2`).

**В PWA.** Пункт: Не начат / Готово / Нужно внимание. Статус пишется в execution state чек-листа. Хаб считает замечания.

**Сейчас в iOS.** `ItemStatus` уже `ok | issue | na`. `ChecklistItemRow2` переключает только ok↔na. `ItemCardView` умеет чип «Проблема», но это не рабочий путь. DEMO-префилл уже может содержать `issue` — в рабочем UI это выглядит как «не сделано».

**Нативный сценарий iOS.** Долгий тап или отдельная кнопка «Проблема» на строке; короткий тап по кружку по-прежнему ok↔na. Пункт с `issue` визуально отличается (например предупреждающий цвет), в прогресс как выполненное **не** входит — как сейчас: в % идут только `.ok`.

**Экраны.** `ChecklistItemRow2`, экраны `*StagesScreen`, `StageDetailView2`.

**Модели.** `StageItem.status` / `ItemStatus.issue`. Новых полей нет.

**Новые поля или сущности.** Нет.

**Миграция.** Нет. Уже сохранённый `issue` просто станет видимым.

**Риск для проектов 1.0.3.** Низкий: decode не меняется. Риск UX — случайно поставить issue вместо ok; снять тем же контролом. Прогресс % не должен начать считать issue как done.

**Сложность.** Средняя (аккуратный UX трёх состояний в плотной строке).

**Ценность.** Высокая.

**Критерии готовности.**

- Короткий тап по-прежнему переключает готово/не готово.
- Можно поставить и снять «Проблема» без потери фото и заметки.
- Read-only / нет подписки по-прежнему блокирует изменение (существующий `isReadOnlyMode`, без правок подписок).
- Префилл DEMO не менять; если в DEMO уже есть issue — только отобразить.
- Проекты 1.0.3 открываются без пересоздания.

**Приоритет.** 1 (вместе с A2).

---

### A2. Лист замечаний на дашборде объекта

**Проблема пользователя.** Чтобы найти все проблемные пункты, нужно открывать каждый этап. Нет счётчика «нужно внимание».

**В PWA.** Кнопка «Внимание · N» на хабе чек-листов, sheet со списком, переход `?highlight=` к пункту.

**Сейчас в iOS.** Дашборд считает % по ProgressStore, листа замечаний нет.

**Нативный сценарий iOS.** На `ProjectDashboardView` блок «Замечания · N». Список: этап, название пункта, переход в `StageDetailView2` (или соответствующий `*StagesScreen`) с прокруткой/подсветкой пункта, если это можно сделать без смены идентификаторов. Deep link веб-формата не копировать.

**Экраны.** `ProjectDashboardView`; навигация в существующие экраны стадий.

**Модели.** Чтение ProgressStore, фильтр `status == .issue`.

**Новые поля.** Нет.

**Миграция.** Нет.

**Риск для 1.0.3.** Низкий: только чтение. Не создавать второе хранилище замечаний. Не менять DEMO-префилл, чтобы «наполнить» список.

**Сложность.** Средняя (навигация к пункту — самая тонкая часть).

**Ценность.** Очень высокая.

**Критерии готовности.**

- Счётчик совпадает с числом `issue` в рабочих паках объекта.
- Пустой состояние: «Замечаний нет».
- Тап открывает нужный этап; пункт находится по существующему UUID/`title` без новых ключей.
- Не использует `Project.stages` таймлайна как источник замечаний.

**Приоритет.** 1 (первая на детальное проектирование).

---

### A3. PDF по рабочим чек-листам

**Проблема пользователя.** «PDF отчёт» с дашборда строится из `project.stages` (таймлайн). Рабочие галочки ProgressStore в файл не попадают. Заказчик не видит реальную приёмку.

**В PWA.** `/checklist-report`: обложка, объект, прогресс, бары этапов, до 80 замечаний. Это не «основной файл объекта».

**Сейчас в iOS.** `ProjectDashboardView.exportPDF` → `PDFReportService.makeProjectReport(project.stages, expenses)`.

**Нативный сценарий iOS.** Новый или расширенный экспорт «Отчёт по чек-листам»: читает те же loader’ы ProgressStore, что дашборд. Старый PDF таймлайна не удалять в этом релизе (два отчёта или явная подпись источника), чтобы не ломать привычку. Веб-pdfmake не переносить: остаётся `UIGraphicsPDFRenderer` / PDFKit.

**Экраны.** Дашборд (меню экспорта), возможно `PDFReportService`.

**Модели.** Только чтение ProgressStore + метаданные проекта.

**Новые поля.** Нет.

**Миграция.** Нет.

**Риск для 1.0.3.** Низкий, если не подменять молча старый файл и не писать в JSON проектов. Риск путаницы двух PDF — снять подписями «Сроки / таймлайн» vs «Рабочие чек-листы».

**Сложность.** Средняя.

**Ценность.** Высокая.

**Критерии готовности.**

- В отчёте видны статусы рабочих пунктов, включая «Проблема».
- Двери и остальные паки — по тем же правилам, что карточка объекта, либо явно подписано, какие паки входят.
- Существующие проекты открываются как раньше; экспорт не меняет диск, кроме создания временного PDF.
- Подписки/DEMO не меняются.

**Приоритет.** 2.

### A4. Поиск по контактам проекта

**Проблема пользователя.** На объекте с десятком подрядчиков нужно листать весь список.

**В PWA.** Локальный поиск по записной книжке + `tel:`.

**Сейчас в iOS.** `ProjectContactsView`: сортировка избранное → имя, CRUD, звонок. Поля поиска нет.

**Нативный сценарий iOS.** `.searchable` или поле фильтра по имени, роли, телефону, комментарию. Пустой результат — понятный empty state. Не добавлять email (в PWA его тоже нет).

**Экраны.** `ProjectContactsView`.

**Модели.** `ProjectContact` без изменений.

**Новые поля.** Нет.

**Миграция.** Нет.

**Риск для 1.0.3.** Нет.

**Сложность.** Низкая.

**Ценность.** Средняя.

**Критерии готовности.** Избранное по-прежнему сверху при пустом запросе; поиск не удаляет контакты; звонок работает.

**Приоритет.** 3 (можно параллельно с PDF).

**Проблема пользователя.** Даже внутри одного этапа длинный список, проблемные пункты тонут.

**В PWA.** Частично закрыто общим листом замечаний, не отдельным фильтром блока.

**Сейчас в iOS.** Список всех пунктов блока.

**Нативный сценарий iOS.** Сегмент Все / Проблемы на `StageDetailView2`.

**Экраны.** `StageDetailView2`.

**Модели.** Нет изменений.

**Новые поля.** Нет.

**Миграция.** Нет.

**Риск.** Нет.

**Сложность.** Низкая.

**Ценность.** Средняя+ (усиливает A1–A2).

**Приоритет.** 2, сразу после листа замечаний, если ёмкость релиза позволяет.

**Сейчас в iOS.** Один пункт «PDF» без пояснения источника.

**Нативный сценарий.** Ясные названия экспортов. Формулы % **не** унифицировать в этом релизе (это уже риск смысла сохранённых ожиданий).

**Влияние на данные.** Нет.

**Приоритет.** Делать вместе с A3, не отдельной большой задачей.

# C. Требуют отдельного проектирования

Затрагивают модели, хранение, миграции или архитектуру. Не начинать в ближайшем релизе.

---

### C1. Тип стен «Каркас»

PWA добавляет ось walls=`frame`. iOS `WallType` этого значения не имеет. Нужен пак чек-листов, иконка, экран стадий, правила merge. Старые проекты без поля продолжат декодироваться, но это уже продуктовое расширение конструктива, не «мелочь UI».

**Миграция.** Формально additive enum, фактически новый контент и ветки UI.  
**Риск.** Средний+, плюс соблазн «заодно поправить» паки.  
**Приоритет.** Отдельная задача после релиза A.

---

### C2. Унификация формул прогресса

Список/дашборд считают ProgressStore без дверей; вкладка План — `AppStore.projectProgress`. Менять формулу — значит изменить «%» у живых пользователей без изменения файлов.

**Риск для 1.0.3.** Смысл сохранённых ожиданий.  
**Не делать** без явного согласования и текста в «Что нового».

---

### C3. Резервное копирование / restore JSON

PWA «бэкап» = сервер. На iOS это экспорт/импорт Documents. Легко получить дубликаты проектов, сломанные пути фото `BC_Media`, разъезд UUID заметок `BCNotes`.

**Миграция / архитектура.** Да.  
**Приоритет.** Отдельный проект. Не обещать паритет с облаком PWA.

---

### C4. Трёхшаговый мастер создания

Не требует новой модели, но перекраивает `NewProject` / пикеры и связан с лимитом USER на создание проекта. Высокий риск задеть paywall и DEMO-вход «как мастер».

**Если мастер когда-нибудь делать** — без изменения правил подписки и без DEMO-ветки.

**Сейчас.** Категория C из-за площади UX и риска задеть создание проекта.

---

### C5. Блокировка смены конструктива как в PWA

PWA не даёт сменить оси после создания. В iOS смена уже есть и полезна. Копировать замок — ухудшение. Если когда-нибудь ограничивать смену, нужно проектировать, что происходит с уже отмеченным ProgressStore (сейчас merge по title). **Не переносить замок PWA.**

---

### C6. iPad split-view / колонки

Только UI, но широкая площадь `MainTabView` / дашборд. Не блокирует 1.0.3 по данным, однако это отдельный дизайн, не «быстрый фикс».

---

### C7. Импорт смет / шаринг объекта / облачная учётка

Новые сущности, идентичность, конфликты. Вне текущего контура.

---

# D. Пока не внедрять

Низкая ценность, высокая сложность, незавершено в PWA, либо задевает подписки / DEMO.

| Тема | Почему D |
| --- | --- |
| ЮKassa, trial 7 дней, checkout | Другой биллинг; iOS = StoreKit. Не трогать |
| Лимит USER, выбор 2 проектов как в вебе, paywall UX | Подписки |
| Restore purchases «как в PWA» | В PWA заглушка; в iOS уже есть StoreKit restore. Не рефакторить |
| DEMO /try-demo, sessionStorage, переход в аккаунт | DEMO |
| Изменение префилла DEMO, чтобы было больше замечаний | DEMO |
| Web Push, service worker, badge, центр уведомлений PWA | Флаги выкл. в PWA; на iOS уже есть локальные task notifications. Не смешивать |
| Онлайн-only синхронизация | Ломает офлайн-преимущество iOS |
| Свободный текст причины задержки вместо enum | Деградация модели iOS |
| Бюджет как JSON-строка PWA | Хрупко, угроза полям план/факт |
| Совместный доступ, роли, мультивалютность, НДС | Нет ни там, ни здесь как продукт |
| Product analytics API | Отдельная privacy-задача |
| mailto «заказать строительство» / лендинг / legal-сайт | Не функции полевого приложения |
| Админка | Не PWA пользователя |
| Повторы задач, исполнители | Нет в PWA, новые поля |
| Склейка ProgressStore в `Project.stages` | Прямой запрет архитектуры iOS |

## Карточки выбранных пунктов ближайшего релиза

Ниже — зачем / почему сейчас / почему безопасно / оставшиеся риски / порядок. Это те же A1–A4.

### 1. Статус «Проблема» в рабочей строке — зачем сейчас

Без этого лист замечаний и честный PDF пусты для обычного пользователя: он физически не может поставить статус в рабочем UI.

**Почему сейчас.** Поле уже в модели 1.0.3; UI просто его не показывает.  
**Почему безопасно.** Нет миграции, нет новых ключей Codable, `%` по-прежнему только `.ok`.  
**Оставшиеся риски.** Перегрузить строку; случайный тап; показать issue из DEMO, не меняя префилл (это допустимо). Не открывать `ItemCardView` как «новый» рабочий путь — не воскрешать мёртвый экран пачкой.  
**Порядок.** Сначала UX-проект строки, затем код (когда будет разрешён).

### 2. Лист замечаний — зачем сейчас

Главный сценарий PWA, которого нет в iOS: «что сейчас красное на объекте».

**Почему сейчас.** Максимум пользы на существующих данных.  
**Почему безопасно.** Только агрегация `issue` из ProgressStore.  
**Риски.** Неверная навигация не туда (таймлайн вместо рабочего этапа); счётчик из `project.stages` вместо ProgressStore; желание «добавить таблицу замечаний» — запрещено.  
**Порядок.** После согласованного UX статуса; проектировать **первым**.

### 3. PDF рабочих чек-листов — зачем сейчас

Пользователи уже жмут «PDF» и получают не те галочки. Это выглядит как баг продукта.

**Почему сейчас.** Экспорт не пишет в проекты.  
**Почему безопасно.** Новый файл во временной директории; старые JSON не меняются.  
**Риски.** Подменить старый отчёт без подписи; включить двери/не включить и разъехаться с % карточки; полезть «заодно» править `PDFReportService` так, что сломается текущий экспорт.  
**Порядок.** После того, как issue видно в UI, иначе раздел замечаний в PDF будет почти пустым у живых пользователей.

### 4. Поиск контактов — зачем сейчас

Мелкая, независимая, безопасная польза. Хороший параллельный кусок, если замечания ещё проектируются.

**Почему безопасно.** Фильтр в памяти.  
**Риски.** Почти нет. Не добавлять поля email «как будто в PWA» — в PWA email контакта нет.

## Функция, которую проектировать первой

**Лист замечаний объекта + постановка статуса «Проблема» в `ChecklistItemRow2`.**

Это один цикл, не две разрозненные фичи:

1. как пользователь ставит проблему, не ломая привычный чекбокс;
2. где видит все проблемы;
3. как переходит к пункту, не изобретая веб-`?highlight=` и не меняя UUID.

Только после согласованного проекта этого цикла имеет смысл писать PDF рабочих чек-листов.

Не проектировать первой: подписки, DEMO, каркасные стены, backup, унификацию %.

## Риски для существующих проектов (сводка)

Даже безопасный релиз A может навредить, если выйти за контур:

- писать замечания в новое поле/файл вместо `ItemStatus.issue`;
- переименовать `issue` / `ok` / `na`;
- считать issue как выполненное в прогрессе;
- строить лист или PDF из `Project.stages` и «починить» это materialize в таймлайн;
- менять title пунктов в JSON-паках;
- добавлять обязательные поля в `Project`;
- менять DEMO-префилл или StoreKit;
- делать миграцию «на всякий случай».

Правило релиза A: **только чтение существующих JSON + запись в уже существующий `status` пункта ProgressStore**, как это делает сегодняшний чекбокс.
