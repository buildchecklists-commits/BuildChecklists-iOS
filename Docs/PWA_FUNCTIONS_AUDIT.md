# BuildChecklists PWA — аудит функций

Дата аудита: 21 сентября 2026.

Источник: фактическая реализация веб-монорепозитория, не README (корневой README описывает устаревший «скелет» без продуктовой логики).

Документ рассчитан на агента без доступа к репозиторию. Вся важная информация зафиксирована здесь, а не через отсылки «смотрите файл X».

| Статус | Значение |

PWA в этом репозитории — клиент apps/web (Next.js 15, React 19, порт 3000). Бэкенд — NestJS 11 + Prisma + PostgreSQL (apps/api, порт 3001, префикс /api). Админка оператора — отдельное приложение apps/admin (порт 3002), это не PWA пользователя.

Язык интерфейса: только русский. Мультиязычности нет.

Юридическое лицо на публичных страницах: ИП Сошникова Анжелика Юрьевна, сайт https://buildchecklists.ru, поддержка support@buildchecklists.ru, телефон +7 903 779-82-52.

## 1. Назначение и основные сценарии

Назначение. Контроль частного строительства дома в одном месте: план этапов, чек-листы приёмки, бюджет и расходы, фотофиксация, файлы, контакты, задачи, PDF/CSV-отчёты. Позиционирование: «Контроль строительства дома в одном приложении». Чипы на лендинге: «План работ», «Чек-листы», «Бюджет», «Фото», «PDF-отчёт».

Кто пользователь. Владелец/заказчик частного дома, прораб, менеджер объекта. Нет организаций, команд, ролей «гость/редактор» внутри проекта. Один аккаунт владеет своими проектами.

Связь с мобильными приложениями. Native iOS и Android живут вне этого репозитория. Контент чек-листов и перечисления конструктивов выровнены с iOS (seeds / Enums.swift). Публичный DEMO веб-клиента сознательно повторяет Android-сидер. Этот документ описывает веб-PWA, а не native.

### Главные сценарии

- Посмотреть демо без регистрации (локальный объект «Дом 160 м²»).

- Зарегистрироваться, взять 7-дневный trial без карты или оплатить тариф USER/PRO через ЮKassa.

- Создать объект: название + 5 осей конструктива (фундамент, стены, перекрытия, форма крыши, покрытие).

- Вести сроки 11 макроэтапов (план/факт).

- Отмечать пункты чек-листов, писать заметки, прикладывать фото, читать справку.

- Фиксировать расходы (материалы / работа / аренда) и сравнивать с плановым бюджетом.

- Хранить фото объекта и документы, вести записную книжку контактов.

- Ставить личные задачи с датой и получать напоминания (если включены серверные флаги).

- Считать материалы калькуляторами (без записи в бюджет).

- Сформировать PDF по чек-листам / бюджету / расходам и CSV по расходам.

## 4. Проекты, планы, этапы, чек-листы, задачи

### 4.1. Проекты

Где: вкладка «Проекты».

Запуск: «+ Новый» → мастер «Объект → Конструктив → Проверка». Карточка открывает дашборд.

Поля объекта

| Поле | UI | Обязательно | Лимит | Когда задаётся |
| --- | --- | --- | --- | --- |
| Название | «Название» | да | 200 | мастер / правка |
| Адрес | «Адрес объекта» | нет | 500 | мастер / правка |
| Кратко о бюджете | в мастере свободный текст; в правке — число ₽ | нет | 500 (строка в API) | мастер: текст; правка: JSON плана |
| Ответственный | «Ответственный / менеджер» | нет | 200 | мастер / правка |
| Цвет карточки | «Фон карточки» | нет | 5 палитр | только правка |
| Обложка | фото origin=PROJECT | нет | — | только правка |
| Даты объекта | план начала/конца | нет | — | экран «Сроки» |
| Конструктив | 5 осей | да при создании | enum | только мастер; потом нельзя сменить |

Конструктив (подписи UI)

- Фундамент: Ленточный, Плита, Свайно-ростверк, ТИСЭ, Комбинированный (strip/slab/pile/tise/combo).

- Стены: Газобетон, Керамоблок, Кирпич, Арболит, Монолит, Керамзитобетон, Комбинированные, Каркас.

- Перекрытия: Монолит, ПБ плита, ПК плита, Плита перекрытия (steel), Деревянное.

- Форма крыши: Плоская, Двускатная, Вальмовая, Мансардная, Односкатная, Многощипцовая, Шатровая, Полувальмовая.

- Покрытие: Металлочерепица, Профнастил, Фальцевая, Гибкая черепица, Керамическая, Композитная, Мембрана/рулонная.

При создании сервер также создаёт: запись конструктива, 11 строк этапов плана, 4 «слота модулей» (PLAN_SHELL, BUDGET_SHELL, PHOTOS_SHELL, CHECKLIST_SHELL) со статусом PLACEHOLDER. Слоты в UI почти не используются (на плане мелькает текст про «заготовку»); реальные модули работают независимо. Статус слота в ACTIVE рабочим кодом не переводится (кроме локального DEMO-сида).

Данные: таблица Project + ProjectConstructionSelection. Чтение списка GET /api/projects, создание POST, правка PATCH /api/projects/:id, удаление DELETE (чистит файлы в storage).

Ограничения

- DEMO: создание проектов в UI выключено.

- READ_ONLY: создание и правки запрещены (403).

- USER: максимум 2 проекта; если уже больше двух и выбор не подтверждён — все объекты только на просмотр, пока пользователь не выберет ровно 2 id.

- Нет шаринга, приглашений, совладельцев.

Статус: реализовано, с оговорками выше.

### 4.2. План и этапы

11 макроэтапов (порядок фиксирован)

- Геология и подготовка участка (geology)

- Фундамент (foundation)

- Стены (walls)

- Перекрытия (slab)

- Крыша (roof)

- Покрытие крыши (roofCover)

- Инженерия (engineering)

- Окна (windows)

- Двери (doors)

- Отделка (finishing)

- Благоустройство (landscaping)

Где: вкладка «План» → выбор объекта → «Сроки».

Запуск: «Открыть план» с дашборда или нижняя вкладка.

Поля этапа: план начало, план окончание, факт начало, факт окончание, причина задержки (до 2000 символов). Плюс период всего объекта.

Статус этапа не задаётся вручную. Клиент может прислать status, сервер игнорирует и считает заново:

- Есть факт окончания → «Завершён»; если факт позже планового дня → «С просрочкой».

- Иначе есть факт начала → «В работе»; если плановый конец уже прошёл → «Просрочен».

- Иначе если плановый конец прошёл → «Просрочен», иначе «Не начат».

Сравнение по календарным дням YYYY-MM-DD (локальный «сегодня» пользователя). Посчитанный статус пишется обратно в БД при сохранении плана.

Сводка плана: число этапов, завершённых, просроченных, в работе, не начатых; процент = округление (завершённые / 11 × 100). «Завершённые» = COMPLETED + COMPLETED_DELAYED.

Данные: Project.planDateStart/End, ProjectPlanStage. API: GET/PATCH /api/projects/:id/plan.

Ограничения: нет зависимостей между этапами, нет ресурсов/бригад, нет Gantt. Чек-лист не двигает статус этапа (даты и чек-лист независимы). Устаревшая строка в shared всё ещё намекает, что «исполнение чек-листа на web пока не ведётся» — это уже неправда.

Статус: реализовано.

### 4.3. Чек-листы

Конвейер контента

- Эталон — iOS seeds.

- Генератор складывает вариативные пакеты в shared (foundation/walls/slab/roof/cover).

- В рантайме materializeStageChecklistTemplate(stageKey, construction) собирает секции.

- Для foundation, walls, slab, roof, roofCover пакет зависит от выбора в мастере.

- Для geology, engineering, windows, doors, finishing, landscaping — общие пакеты; конструктив только подписью «Конструктив проекта: …».

- В БД хранятся только статусы и заметки по ключу (projectId, stageKey, itemKey). Тексты пунктов в БД не дублируются.

Иерархия экранов

- Хаб: 11 строк, прогресс, кнопка «Внимание · N».

- Этап: список блоков (один блок = одна секция сида).

- Блок: пункты, тоггл «готово», цикл внимания, sheet заметки, фото, справка.

Статусы пункта: Не начат / Готово / Нужно внимание.

Справка: у пункта может быть infoSlug → markdown из каталога info-texts (сотни файлов по дверям, инженерии, отделке, перекрытиям, фундаменту, ландшафту, крыше, участку, стенам, окнам). Если слага нет: «Для этого пункта пока нет справки».

Данные: ProjectStageChecklistItem + шаблоны shared + ProjectPhoto origin CHECKLIST_ITEM. API: GET checklist-hub, GET plan/:stageKey, PATCH plan/:stageKey/checklist, загрузка фото пункта.

Ограничения: конструктив после создания не меняется — иначе старые ключи пунктов могут не совпасть с новым пакетом. Нет тредов комментариев, нет назначения исполнителя, нет обязательных фото. Прогресс чек-листа считается по пунктам (done/total), отдельно от прогресса плана по датам.

Статус: реализовано.

### 4.4. Задачи

Где: /app/tasks («Календарь задач»). С дашборда: «Создать задачу» / «Открыть все задачи» с ?projectId= и опционально ?create=1.

Поля: заголовок (≤180), подробности (≤2000), срок (ISO datetime или «Без срока»), флаг выполнено, необязательный projectId. Нет приоритета, повторов, вложений, исполнителей.

Календарь: полоса недели, месяц, выбор дня, «Показать выбранный день». Фильтры: Все / Сегодня / Просрочено / Выполнено. Поиск по title+details локально. Сортировка фиксирована: просроченные → ближайшие → без даты → выполненные.

Напоминания: при создании/смене срока, если задача не выполнена и срок уже наступил — вид TASK_REMINDER_DUE. При завершении — TASK_COMPLETED. Воркер/планировщик (флаги, по умолчанию выкл.) добавляет «на сегодня» и «просрочена». Часовой пояс по умолчанию Europe/Moscow.

Данные: таблица Task (владелец — пользователь; проект опционален, при удалении проекта projectId обнуляется). API: GET/POST /api/tasks, PATCH/DELETE /api/tasks/:id.

Заглушка: /app/projects/[id]/tasks показывает «Заготовка раздела… как секция в iOS», живой список туда не подключён.

Статус: глобальный календарь реализован; проектный маршрут — заготовка; push/in-app зависят от флагов.

## 5. Бюджет, расходы, категории, валюты, расчёты

Категории расходов — ровно три вида (как iOS ExpenseSubCategory): Материалы, Работа, Аренда техники. Отдельного справочника категорий нет.

Валюта: только RUB. Поле валюты у расхода отсутствует. UI форматирует через Intl RUB.

Хранение суммы: amountMinor — целое число копеек. Пользователь вводит рубли, клиент делает Math.round(n * 100). Диапазон API: 1…9_999_999_999 копеек. Комментарий ≤ 2000. Дата YYYY-MM-DD. Привязка к макроэтапу обязательна.

Плановый бюджет не отдельная таблица. Строка Project.budgetSummary хранит JSON:

{ "v": 1, "totalMinor": number|null, "byStageMinor": { "<stageKey>": number } }

Старый свободный текст: из него вытаскивается первое число как рубли × 100 (только итог). В мастере создания поле ещё текстовое («Кратко о бюджете / смете»); после правки объекта обычно становится JSON.

Экран настройки: «Общий бюджет проекта, ₽» + «План по этапам» (пусто = не задано). Если сумма этапов ≠ итогу — мягкий диалог «Обновить общий бюджет по сумме этапов» / «Сохранить как есть».

Формулы (факт = сумма expenses.amountMinor, с учётом фильтров на операционном срезе)

| Метрика | Формула |
| --- | --- |
| Остаток | план − факт |
| Отклонение | факт − план |
| Освоено, % | округление (факт / план × 100), не ниже 0 |
| Δ этапа | факт этапа − план этапа (null, если плана нет) |
| Перерасход этапа | факт > план, сумма = факт − план |
| Доля вида/этапа | округление (часть / факт × 100) |

Статусы UI: «Бюджет не настроен» / «Есть перерасход» / «В пределах бюджета».

График расходов: горизонтальные доли по этапам и по видам, не временной ряд. В PDF бюджета дополнительно накопительный факт по датам.

CRUD: только GET список с фильтрами и POST создание. Нет PATCH/DELETE расхода — ошибочную запись нельзя поправить.

Калькуляторы не пишут в бюджет. Это отдельные клиентские формулы (объём бетона с запасом 5% по умолчанию, арматура плита/лента ⌀6–20, доска по размерам или площади, кладка с проёмами и запасом, штукатурка/шпаклёвка кг и мешки, утеплитель упаковки или м³).

Статус: учёт факта и план/факт реализованы; нет счетов, НДС, вложений к расходу, мультивалюты, правок/удаления, импорта.

## 7. Календарь, сроки, напоминания, статусы

Три независимых «календаря»:

- Сроки строительства — даты объекта и 11 этапов (раздел 4.2). Нет напоминаний «этап просрочен» в notification center; просрочка видна статусом на плане.

- Календарь задач — единственный интерактивный календарь (неделя/месяц).

- Группировка фото по времени — не календарь ввода.

Напоминания задач (если флаги включены)

| Вид | Заголовок | Приоритет | Когда | Push? |
| --- | --- | --- | --- | --- |
| TASK_REMINDER_DUE | Напоминание по задаче | HIGH | срок наступил / планировщик | да, если push включён |
| TASK_OVERDUE | Задача просрочена | HIGH | CLI-воркер, календарный день в TZ | да |
| TASK_DUE_TODAY | Задача на сегодня | NORMAL | CLI-воркер | нет (push только HIGH) |
| TASK_COMPLETED | Задача выполнена | NORMAL | сразу при завершении | нет |
| BILLING_RENEWAL_FAILED | Не удалось продлить подписку | HIGH | сбой renewal | да |
| BILLING_SUBSCRIPTION_EXPIRED | Подписка истекла | HIGH | истечение / grace expiry | да |

Дедуп ключами вида task-due-today:{id}:{dayKey}. Интервал внутри Nest по умолчанию обрабатывает только reminder-due; due-today и overdue рассчитаны на CLI task-notifications:worker + cron. По умолчанию NOTIFICATIONS_INAPP_ENABLED, NOTIFICATION_TASK_PRODUCERS_ENABLED, TASK_REMINDER_SCHEDULER_ENABLED, NOTIFICATION_PUSH_ENABLED = false (нужна строка "true"). UI колокольчика: NEXT_PUBLIC_NOTIFICATIONS_UI_ENABLED, push-карточка: NEXT_PUBLIC_PUSH_UI_ENABLED, badge: NEXT_PUBLIC_APP_BADGE_ENABLED — тоже false, пока не заданы при сборке.

Статусы в продукте (сводка)

- Подписка: DEMO, TRIAL, ACTIVE_USER, ACTIVE_PRO, EXPIRED, PENDING, GRACE, CANCEL_AT_PERIOD_END.

- Доступ: DEMO, USER, PRO, READ_ONLY.

- Этап плана: Не начат / В работе / Завершён / С просрочкой / Просрочен.

- Пункт чек-листа: Не начат / Готово / Нужно внимание.

- Задача: булев isCompleted.

- Слот модуля: Заготовка / Активно (почти не используется).

## 8. Фото, файлы, комментарии, контакты

### Фото

Два происхождения: PROJECT (фото объекта, без stage/item) и CHECKLIST_ITEM (обязательны stageKey + itemKey). Хранение: ключ projects/{projectId}/{uuid}.jpg|png.

Лимиты: Multer 10 МиБ, сервис отклоняет > 9 МиБ. Только JPEG/PNG по magic bytes (FF D8 FF / PNG signature). Клиент перед загрузкой сжимает (длинная сторона ≤ 2000px, JPEG q=0.88). Подпись ≤ 500. UI accept шире (в т.ч. HEIC/WebP) — такие файлы на сервере часто падают, если клиент не сконвертировал.

Удаление фото есть. Просмотр: единая лента, бакетирование по давности, карточка с полями Объект / Этап / Источник / Пункт / Подпись.

### Файлы

Категории: DOCUMENT (много) и PRIMARY (ровно один на проект; новый upload заменяет старый и удаляет файл). Ключ: projects/{projectId}/files/{uuid}.{ext}. Лимит 15 МиБ. MIME: pdf, jpeg/jpg, png, webp, heic. Имя ≤ 255. Сообщения: «Файл слишком большой (максимум 15MB)», «Допустимы PDF и изображения (JPEG/PNG/WEBP/HEIC)».

Экран объекта: секции «Документы» и «Основной файл проекта». Основной PDF открывается на /project-document canvases pdf.js.

### Комментарии

Отдельной сущности «комментарий/чат» нет. Есть:

- заметка пункта чек-листа (note, пустое сохранение удаляет);

- «Комментарий» у контакта (поле note, ≤ 4000);

- «Комментарий» у расхода (≤ 2000);

- caption фото.

Нет тредов, лайков, упоминаний, комментариев к фото как дискуссии.

### Контакты

Только в контексте проекта. Поля: имя 1–500, роль ≤ 500, телефон 1–80, заметка ≤ 4000, избранное. CRUD + tel:. Публичная страница /contacts — реквизиты компании, не записная книжка объекта.

## 9. Импорт, экспорт, PDF, CSV

Импорта проектов, расходов, чек-листов, контактов нет.

Экспорт расходов (/api/projects/:id/expenses/export, уважает текущие фильтры):

- CSV: BOM UTF-8, разделитель ;. Служебные строки «Проект:», «Фильтры:», «Итого по выборке: … ₽». Колонки: Дата; Этап; Тип расхода; Сумма (₽); Комментарий. Сумма с запятой как десятичным разделителем.

- PDF внутренний: «Отчёт по расходам» — объект, фильтры, итог, сводка по этапам, список.

- PDF клиентский: включатели итога / по этапам / детализации, даты, комментарии, необязательная заметка заказчику.

Пустая выборка → 422 «По текущей выборке нет расходов…». В read-only кнопка экспорта скрыта.

Экспорт бюджета — только PDF (нет CSV): KPI, план/факт, внимание, дорогие позиции, разрезы, операционный список.

PDF чек-листов: обложка BuildChecklists, объект, адрес, менеджер, общий прогресс, счётчики статусов плана, бары по этапам, до 80 замечаний. Явно не является «основным файлом объекта».

Генерация: pdfmake на стороне Next BFF (не отдельный Nest ExportsModule — тот модуль пустой).

Share sheet / AirDrop / системный шаринг не реализованы.

## 10. Отчёты и статистика

Пользователь видит только отчёты своего объекта:

- дашборд: % готовности (из чек-листов и/или плана — на карточке сводка плана и хаба), даты, счётчик внимания, ближайшая задача, строка расходов;

- бюджетные KPI и план/факт;

- график долей расходов;

- PDF/CSV из раздела 9.

Нет пользовательского дашборда по всем объектам (кроме списка карточек и глобальной ленты фото). Нет финансовых аналитических срезов «за год / все объекты».

Product analytics пишется в ProductAnalyticsEvent (без PII): старт демо, шаги тура, регистрация, trial, покупки USER/PRO, создание проекта/задачи/расхода, фото, документ, отметка чек-листа, калькулятор. Смотрит это админ, не пользователь PWA.

Сессии устройств (UserDevice, heartbeat раз в ~10 мин с клиента / 15 мин на сервере): платформа, PWA да/нет, locale, timezone, lastPath, push. Тоже админ.

## 11. Авторизация, профили, права

### Сессия

- JWT в httpOnly cookie bc_access_token, Path /, SameSite Lax, Secure в prod, Max-Age 7 дней (совпадает с JWT_EXPIRES_IN по умолчанию 7d).

- Браузер не ходит в Nest с cookie. Next BFF читает cookie и ставит Authorization: Bearer.

- Демо-cookie bc_demo_session=1 (не httpOnly, 7 дней) только пускает в /app без JWT. Сам режим DEMO на клиенте держится sessionStorage; одной cookie недостаточно.

После регистрации/логина демо-сессия сбрасывается.

### Auth API

- POST /auth/register — 3 запроса/мин с IP

- POST /auth/login — 5/мин

- POST /auth/forgot-password — 5/час

- POST /auth/reset-password — 10/мин

- GET /auth/me

- DELETE /auth/account

- Глобальный антифлуд: 120 запросов/мин на маршрут без своего лимита. Аварийно выключается RATE_LIMIT_DISABLED=1.

Новый пользователь: productAccessMode=USER, subscriptionState=PENDING → эффективно READ_ONLY, пока не trial или оплата.

Профиль: отображаемое имя = локальная часть email (не отдельное поле ФИО). Нет аватара пользователя, нет смены email, нет 2FA, нет OAuth/Apple/Google.

Листы профиля «Предложить идею» и «Заказать строительство» открывают mailto:support@buildchecklists.ru — в БД не пишутся.

### Права (не RBAC)

Эффективный режим из подписки:

- Если оплаченный период кончился по календарю при ACTIVE_*/CANCEL_AT_PERIOD_END → READ_ONLY.

- Иначе явный DEMO / READ_ONLY.

- CANCEL_AT_PERIOD_END при живом периоде сохраняет USER/PRO.

- Иначе: TRIAL/ACTIVE_USER → USER; ACTIVE_PRO → PRO; EXPIRED/PENDING/GRACE → READ_ONLY.

isProjectReadOnly:

- READ_ONLY — всегда;

- PRO и DEMO — никогда;

- USER + «нужно выбрать 2 проекта» — все read-only;

- USER + подтверждённый список — только эти id можно менять; пустой список → все можно.

Создание проекта: запрещено в read-only и пока не выбран whitelist; у USER лимит 2.

Админ: флаг User.isAdmin вручную в БД. AdminGuard требует isAdmin и отвергает DEMO. UI apps/admin открывается любому залогиненному (middleware смотрит только cookie), но API вернёт 403 без флага. Это не часть PWA.

## 13. DEMO-режим

Существует и это основной маркетинговый вход. Это не пользователь с productAccessMode=DEMO в PostgreSQL. Серверного демо-аккаунта публичный поток не создаёт.

Как запускается: /try-demo → activatePublicDemoSession(): сброс тура, sessionStorage-флаги, UUID сессии, cookie bc_demo_session=1, сид рантайма, событие demo.started, редирект /app/projects. Клиент подменяет access snapshot на DEMO с canEditContent: true.

Сид выровнен с Android DemoProjectSeeder:

- id demo-project-foundation, имя «Дом 160 м² (пример)»;

- адрес: Московская область, Наро-Фоминский г.о., д. Хлопово;

- менеджер «Прораб Олег»;

- конструктив: лента + газобетон + монолит + двускатная + металлочерепица;

- план февраль–сентябрь 2026, бюджет 12 000 000 ₽ с разбивкой по этапам;

- расходы и фото из локальных SVG public/demo/android-parity/.

Правки чек-листа, плана, расходов, фото живут в sessionStorage ключе buildchecklists.demoRuntime.v1. Закрытие вкладки / регистрация / логин стирают демо. Миграции в аккаунт нет.

Тур (6 шагов): объект → дашборд → чек-листы → отметка пункта → план → фото. После — промпт «В демо данные не сохраняются. Создайте аккаунт…» (Создать аккаунт / Позже).

После удаления профиля клиент снова включает локальный DEMO («следующая сессия откроется в демо-режиме»).

Оплата в демо недоступна: «В режиме демо оплата недоступна…».

Идентификаторы: User/Project/Task/Photo/File/Contact/Expense/ChecklistItem — UUID; биллинг/уведомления/push/device — часто cuid.

## 16. Что особенно полезно переносить в iOS

Имеется в виду продуктовая семантика и домен, а не копирование Next/Nest.

- Вариативные чек-листы по конструктиву — ядро продукта; на iOS это уже источник правды. Веб подтверждает ту же модель ключей пунктов и трёх статусов + заметка + фото + infoSlug.

- 11 макроэтапов и движок статуса из план/факт дат — простые правила, хорошо ложатся на native календарь.

- Расходы: 3 вида × этап, копейки, только RUB — компактная модель для мобильного ввода на площадке.

- Единая лента фото (объект + пункты) с группировкой по времени — сильный полевой сценарий.

- Контакты объекта с избранным и tel: — типичный mobile pattern.

- Календарь задач с фильтрами Сегодня/Просрочено — native Calendar/Reminders-like UX.

- Режим USER: 2 редактируемых проекта — уже завязан на Android-like правила; iOS должен совпадать, иначе биллинг разъедется.

- Trial 7 дней без карты и каталог цен USER/PRO.

- DEMO без сервера + тур — хороший onboarding; на iOS лучше опираться на существующий Android/iOS seeder, не на sessionStorage веба.

- Справки info-texts — готовый контент приёмки, критичен в поле без прораба под боком.

- Калькуляторы материалов — удобны офлайн на стройке (в вебе как раз не сохраняются — для iOS логично считать локально).

- PDF отчёты для заказчика (чек-листы, бюджет, расходы) — ценность «показать на встрече».

- Access snapshot как единый контракт (mode, readOnly, whitelist) — чтобы web/iOS/Android не расходились в read-only.

## 17. Слабые места: не переносить в iOS без переработки

- Архитектура BFF + httpOnly cookie. Для iOS нужен прямой API + secure token storage (Keychain), refresh-стратегия, а не копирование Next route handlers.

- PWA без offline. На площадке сеть плохая: очередь фото, локальный черновик чек-листа, конфликт-мердж. Веб это не решает — слепо тащить «только online fetch» нельзя.

- DEMO в sessionStorage без миграции в аккаунт. Пользователь потеряет работу. На iOS нужен либо явный sandbox с экспортом, либо серверный guest.

- Расход нельзя изменить или удалить. Для мобильного ввода с опечатками это дефект модели, не «простое API».

- Плановый бюджет как JSON-строка плюс легаси-текст. Нужна нормальная сущность plan lines, иначе отчёты и синхронизация будут хрупкими.

- Конструктив неизменяем. Смена типа фундамента на объекте — реальный кейс; веб оставляет сиротские itemKey.

- Слоты модулей PLACEHOLDER и пустые Nest-модули (checklist, budget, expenses, exports, demo, templates, timeline, audit) — шум, не архитектура для native.

- Маршрут задач проекта — заглушка, живые задачи глобальные. На iOS секция «Задачи проекта» уже ожидается; не копировать заглушку.

- Уведомления выключены флагами; due-today/overdue только CLI. Для iOS — UserNotifications + серверные silent/push по единым правилам, не web-push VAPID и не «не забыть cron».

- HEIC: камера iOS даёт HEIC, веб-API принимает в основном JPEG/PNG. Native должен либо конвертировать, либо API должен принимать HEIC явно.

- Нет шаринга объекта с прорабом/заказчиком. Веб однопользовательский; для iOS это, скорее, будущая фича, а не порт текущей модели User→Project.

- Формы «идея» / «заказ строительства» через mailto. На iOS лучше нативная форма + API или просто Deep link в Mail — не строить продукт вокруг mailto.

- «Восстановить покупки» — заглушка веба; у iOS это StoreKit, другой контур, нельзя имитировать кнопкой-toast.

- Email verification не работает. Не опираться на emailVerifiedAt.

- Кастомных категорий расходов, НДС, счетов, импорта Excel нет — не обещать паритет с «полной сметой».

- Админка в /admin web-приложения пустая; настоящая админка — другой деплой. Не тащить в iOS.

- Feature flags по умолчанию выключают автопродление, сохранённые карты, push, in-app. Порт «как в проде local» занизит ожидания.

- Календарные дни статуса этапа завязаны на локальную таймзону браузера. На iOS зафиксировать TZ объекта или устройства явно.

- Нет полнотекстового поиска по пунктам — на стройке с длинными чек-листами это боль; веб-поиск копировать не стоит как эталон.

- Устаревшие копирайты («заготовки разделов», «привязка к этапам появится», «чек-лист на web не ведётся», авто-trial в туре) — не переносить тексты слепо.

- Доступ однопользовательский: DEMO локальный, USER/PRO/trial на сервере, USER ограничен двумя редактируемыми объектами.

- Самые зрелые модули: проекты, план-даты, чек-листы, фотолента, контакты, глобальные задачи, расходы-как-журнал, PDF.

- Самые дырявые для порта на iOS: offline, правка расходов, бюджет-JSON, неизменяемый конструктив, уведомления за флагами, биллинг ЮKassa vs StoreKit, отсутствие шаринга.

- Не копировать веб-инфраструктуру (BFF, cookies, пустые Nest-модули, sessionStorage DEMO). Копировать доменные инварианты и пользовательские сценарии.
