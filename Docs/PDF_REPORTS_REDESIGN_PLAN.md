## 1. Что уже есть

Генерация везде через `UIGraphicsPDFRenderer`. `PDFKit` только показывает готовый файл. HTML и WebView для сборки страниц нет.

Рядом лежит уже принятый план рабочих чек-листов: `Docs/CHECKLIST_PDF_REPORT_IMPLEMENTATION_PLAN.md`. Его контракт не переписывать. Этот документ описывает всю систему отчётов и не заменяет тот план.

### 1.1. «PDF проекта»

Откуда: дашборд, быстрое действие «PDF проекта» (`project.quickAction.projectPDF`).
Цепочка: `ProjectDashboardView.exportPDF` → `PDFReportService.makeProjectReport` → `Components/ShareSheet.swift`.

Сервис: `Services/PDFReportService.swift`.
Модели: `Project`, массив `project.stages` (`Stage` / `StageItem`), `store.expenses(for:)`.

В PDF реально входит:

- заголовок «Отчёт по проекту», имя, адрес, `dateStart`, `dateEnd`, ответственный, строка «Сгенерировано»;
- раздел «1. Чек-листы по этапам» по `project.stages`: название, subtitle, пункты со значками ✅ / ⚠️ / ◻️ и `StageItem.note`;
- раздел «2. Расходы по проекту», только если расходы не пустые: итог, суммы по `ExpenseCategory.title`, детализация по дате с категорией и `note`.

Фильтры не применяются. Фото, контакты, задачи, плановые суммы по этапам, фактические даты этапов и замечания из рабочих пакетов не входят.

Аудитория по содержанию — владелец: есть построчные расходы и внутренние заметки пунктов. Отдельного заказчицкого режима нет.

Файл пишется в Documents: `BC_Report_<имя>_<unix>.pdf`. В `projectPDFPath` и JSON путь не записывается. Старые файлы не удаляются. Ошибка только в `print`, без сообщения на экране.

### 1.2. «PDF чек-листов»

Откуда: дашборд, быстрое действие «PDF чек-листов» (`project.quickAction.checklistPDF`).
Экран: `Views/Projects/ChecklistReportExportView.swift`.

Сервисы:

- сборка снимка: `Services/ChecklistReportSnapshot.swift` (`ChecklistReportSnapshotBuilder`);
- рисование: `Services/ChecklistReportPDFRenderer.swift`;
- временный файл: `Services/ChecklistReportExportFile.swift`;
- чтение пакетов: `ChecklistPackStore.load` без записи и без merge шаблона.

Модели снимка: поля проекта в памяти (`ChecklistReportSource`), 11 пакетов `ChecklistPack`, этапы и пункты, прогресс, текст `BCNotes`, пути фото замечаний.

Настройки экрана:

- «Полный отчёт» или «Только замечания» (`ChecklistReportScope`);
- «Включить фотографии».

В PDF входит титул, сводка, при полном режиме все 11 пакетов, затем раздел замечаний. Прогресс шапки — среднее 10 пакетов без дверей, та же формула, что у карточки. Двери остаются в теле со своим процентом. Непрочитанный пакет не молчит: текст «Данные пакета не прочитаны.» Фото замечания — не больше 8 кадров.

Фильтры периода, этапа бюджета и типа расхода не используются.

Аудитория — рабочий отчёт владельца и прораба: статусы, замечания, заметки и фото. Для заказчика отдельного усечения нет.

Файл во временном каталоге, имя `BuildChecklists_<имя>_<yyyy-MM-dd_HHmmss>.pdf`. В проект не сохраняется. Share Sheet на iPad якорится через `checklistReportConfigurePopover`.

### 1.3. «PDF (все)»

Две точки входа в один метод `AppStore.exportExpensesPDF(for:)`:

- бюджет проекта, `Views/Budget/BudgetProjectView.swift`, кнопка `ShareLink` с подписью «PDF (все)»;
- `Views/Expenses/ExpensesExportView.swift`, кнопка «PDF-отчёт по расходам (список)». Экран открывается из `ProjectExpensesView`.

Данные: все `ExpenseItem` проекта, сортировка по дате. Фильтры списка бюджета (этап, тип, период, поиск) не передаются. Если расходов нет, метод возвращает `nil`.

В PDF: «Отчёт по расходам», имя проекта, псевдотаблица «Дата / Этап / Тип / Сумма / Комментарий». Итога нет. Группировки нет.

Аудитория — владелец: виден каждый платёж и комментарий.

Файл: временный `Expenses-<имя>.pdf`. Повторная запись затирает тот же путь.

### 1.4. «PDF для заказчика»

Тот же два входа, метод `AppStore.exportCustomerExpensesPDF(for:dateFrom:dateTo:)`:

- на бюджете `ShareLink` «PDF для заказчика» передаёт период, только если включён общий тумблер «Фильтр по дате»;
- на `ExpensesExportView` кнопка «PDF-отчёт для заказчика» передаёт даты «от» и «до» независимо. Если «от» позже «до», даты меняются местами.

Пикеры «Этап строительства» и «Тип расхода» на `ExpensesExportView` в генератор не передаются. Подпись кнопки говорит «с учётом фильтров», но код фильтрует только даты. На экране бюджета этап и тип тоже фильтруют список операций, но не этот PDF. Подпись там честная: «PDF для заказчика учитывает фильтр по датам, если он включён.»

В PDF: заголовок «Отчёт по расходам для заказчика», проект, период если задан, итог, группы по `ExpenseCategory` и внутри суммы по `ExpenseSubCategory`, итог этапа. Построчных операций, комментариев, контактов и чек-листов нет.

Аудитория — заказчик: свёрнутые суммы без внутренних заметок.

Пустой результат после фильтра даёт `nil` и текст ошибки на экране экспорта. На бюджете `ShareLink` в этом случае просто не показывается.

Файл: временный `Expenses-Customer-<имя>.pdf`.

### 1.5. CSV

Не PDF, но на тех же экранах: `exportExpensesCSV`. Колонки «Дата;Этап;Тип;Сумма;Комментарий», все расходы, без фильтров. Его нельзя ломать при переработке PDF.

Поиск по `UIGraphicsPDFRenderer` даёт только `PDFReportService`, два метода в `AppStore` и `ChecklistReportPDFRenderer`.

## 2. Проблемы текущих генераторов

### 2.1. «PDF проекта»

- Чек-листы берутся из `project.stages`, а рабочие отметки дашборда живут в 11 хранилищах пакетов. Пользователь не увидит в этом PDF то, что отметил в рабочем чек-листе. Заметки `BCNotes` и фото замечаний сюда не попадают. Это уже зафиксировано в плане чек-листов. Кнопку на пакеты не переключать.
- Цвета `.label` и `.secondaryLabel`. Страница PDF белая. В тёмной теме системный текст может стать белым на белом.
- Даты через `DateFormatter.dateStyle = .medium` без явной локали. У нелокализованного приложения месяц может оказаться английским.
- Сумма через `NumberFormatter` с `currencyCode = "RUB"` и без фиксированной локали. Вид валюты зависит от системы.
- Нет колонтитула, номера страницы и повтора заголовка раздела.
- `newPageIfNeeded` переносит блок только если он целиком ниже остатка страницы. Строка выше высоты страницы всё равно рисуется и вылезает за край.
- Значки ✅ ⚠️ ◻️ в PDF ненадёжны: часть просмотрщиков заменяет их пустым местом. Статус не дублируется словом.
- Ошибка генерации не показывается пользователю.
- Share Sheet без якоря popover. На iPad лист может не открыться.
- Файл остаётся в Documents навсегда.

### 2.2. «PDF чек-листов»

Это самый собранный генератор: белая заливка, Arial с запасным системным шрифтом, кириллица, `ru_RU`, дата `dd.MM.yyyy HH:mm`, колонтитул, «Стр. N», перенос по словам, запас под колонтитул, ограничение фото.

Оставшиеся границы, их не чинить в чужих этапах:

- номер страницы без общего числа: второй проход не делается;
- заголовок пакета на следующей странице не повторяется как «продолжение», если этап переехал;
- цвет статуса зелёный и оранжевый. В чёрно-белой печати он должен дублироваться словом, слова уже есть;
- превью `PDFView.backgroundColor = .systemBackground` зависит от темы приложения. Сам PDF белый.

Текущее поведение этого отчёта сохраняется до отдельного решения о миграции.

### 2.3. Расходы, оба PDF

- Страница 595.2×841.8, поля 40. Заголовок таблицы расходов — одна строка пробелов, не колонки. Длинный этап и комментарий наезжают на сумму.
- Комментарий рисуется через `CTFramesetter` с фиксированным сдвигом `y += 24` и переворотом контекста. Длинный текст обрезается и может наложиться на следующую строку. На новую страницу комментарий не переносится.
- Новая страница списка не повторяет заголовок колонок.
- Суммы: десятичный формат, группировка пробелом, 0 знаков после запятой, без «₽». Копейки отбрасываются, а не показываются.
- Даты `dd.MM.yyyy` без явной локали календаря. Для этой маски вид стабилен, но это третий способ форматировать дату.
- Сравнение периода — сырой `Date`, не начало и конец дня. Дата «по», выбранная календарём как полночь, отсекает расходы этого дня с ненулевым временем.
- У заказчицкого PDF нет номеров страниц и колонтитула.
- Заголовок группы может остаться на предыдущей странице, а строки уйти на следующую.
- `ExpensesShareSheet` без popover. `ShareLink` на бюджете системный и для iPad обычно безопаснее, но это другой механизм.
- Пикеры этапа и типа на экране экспорта выглядят как фильтр PDF и молча не работают.

### 2.4. Общие дубли

Три независимых рисовальщика копируют:

- размер A4 с двумя разными прямоугольниками;
- шрифты и ручной `cursor`;
- формат даты и денег;
- шапку «проект / имя»;
- перенос страницы без общего правила «не рвать блок».

Итоги расходов считаются и в `PDFReportService`, и в `AppStore`. План/факт уже считается в `AppStore.planFactByStage`, но ни один PDF его не печатает.

## 3. План/факт: что уже есть

Новые поля не добавлять. Ниже только то, что уже хранится.

### 3.1. Деньги

План:

- `Project.budget` — одна сумма проекта;
- `Project.plannedBudgetByStage` — словарь `GlobalStageCategory` → `Decimal`. Пустой у старых проектов. Редактор: `BudgetPlanEditorView`.
- `AppStore.plannedBudget`, `plannedBudgetTotalsByStage`, `planFactForStage`, `planFactByStage`.

Факт:

- `ExpenseItem.amount`, `date`, `category` (`ExpenseCategory`), `subCategory`, необязательные `stageCategory` и `stageItemID`, `note`.
- Факт этапа: `AppStore.totalsByStageCategory`. Если `stageCategory` задан, сумма идёт в него. Если нет, категория расхода отображается на глобальный этап. У `ExpenseCategory` нет «Покрытия крыши»: такой расход без `stageCategory` попадает в `.roof`, не в `.roofCover`.
- Факт покрытия крыши есть только у расходов, у которых явно записан `stageCategory == .roofCover`.

Связь денег по этапам корректна без изменения моделей: ключ `GlobalStageCategory`. Это 11 значений, те же имена, что у пакетов чек-листа. `stageItemID` связывает расход с пунктом, но для отчёта план/факт по пунктам плана нет: плановой суммы пункта не существует.

`project.budget` и сумма `plannedBudgetByStage` могут разойтись. Экран бюджета при сохранении плана записывает в `budget` сумму этапов. Старые проекты могут иметь только общий `budget` без словаря. Отчёт должен печатать обе величины отдельно и не подменять одну другой.

### 3.2. Сроки

Уже есть:

- проект: `dateStart`, `dateEnd`;
- этап таймлайна `project.stages`: `plannedStart`, `plannedEnd`, `actualStart`, `actualEnd`, `delayReason`, `delayComment`, вычисляемый `Stage.status`.

Эти этапы — контур `ProjectPlanView` и `project.stages`. У них нет поля `GlobalStageCategory`. Совпадение названия этапа с названием глобальной категории не гарантировано и не является ключом.

Поэтому без новых полей можно честно напечатать две отдельные таблицы:

1. деньги: план, факт, разница по `GlobalStageCategory`;
2. сроки: план и факт по строкам `project.stages`, где есть хотя бы одна дата.

Нельзя склеить их в одну строку «этап = деньги + даты + процент чек-листа». Процент чек-листа живёт в пакете, даты — в `project.stages`, деньги — в глобальной категории. Общее у них только человекочитаемое имя.

Отклонение в днях считается на лету, если есть `plannedEnd` и `actualEnd`: разность календарных дней. Если факт ещё не закрыт, сравнивать «сегодня» с `plannedEnd` можно только как статус «идёт / просрочен», и только когда `Stage.status` уже даёт `.delayed`. Не выдумывать дату факта.

### 3.3. Чего нет

- плановой суммы на `Stage` и на пункте чек-листа;
- внешнего ключа от `Stage` к `GlobalStageCategory` и к `ChecklistPack`;
- плановой суммы именно на покрытие крыши в `ExpenseCategory` (она есть только в `plannedBudgetByStage`);
- отдельного «заказчицкого» бюджета;
- факта, привязанного к `project.stages.id`.

Утверждено: отчёт «План/факт» — две независимые таблицы. Деньги идут по `GlobalStageCategory`. Сроки идут по строкам `project.stages`. Строки не объединяются по названиям. Ключи в модели не добавляются.

График «План/факт бюджета» показывается только когда одновременно есть план больше 0 и факт больше 0. Если есть только план, печатается таблица без графика. Если есть только факт, график сравнения не строится; отдельный график структуры расходов допустим лишь при двух и более ненулевых категориях. Одна категория остаётся таблицей. Если нет ни плана, ни факта, денежный блок скрыт.

## 4. Целевая система

Пять документов. Старые кнопки их не вызывают, пока не будет этапа миграции.

| Документ в интерфейсе | Для кого | Основа | Когда пустой раздел скрывается |
| --- | --- | --- | --- |
| Сводный отчёт | Владелец | рабочие пакеты, замечания, расходы; задачи и контакты только если пользователь включил их | Пустой раздел не печатает заглушку, кроме явной фразы на титуле, если данных совсем нет |
| Отчёт для заказчика | Заказчик | проценты чек-листов и краткий прогресс по пакетам, свёрнутые расходы, факт просрочки и даты без причины | То же |
| Чек-листы | Владелец | текущий `ChecklistReportPDFRenderer` без смены контракта | Как сейчас |
| Расходы | Владелец | операции с фильтрами нового экрана | Нет операций — не создавать пустой файл, показать причину |
| План/факт | Владелец | таблица денег по `GlobalStageCategory` и отдельно таблица сроков по `project.stages` | Блок денег скрыт, если нет плана и факта. Блок сроков скрыт, если ни у одного этапа нет дат |

В интерфейсе новый документ называется «Сводный отчёт». Так он не смешивается со старой кнопкой «PDF проекта»: та до миграции читает `project.stages`, новый документ читает рабочие пакеты.

Заказчицкий документ включает проценты чек-листов и краткий прогресс по пакетам. Он не включает внутренние пункты, замечания по пунктам, `note` расходов, `BCNotes`, фото, задачи, телефоны и причины просрочки (`delayReason`, `delayComment`). Сам факт просрочки и даты показывать можно.

Пресет владельца по умолчанию включает чек-листы, замечания и расходы. Контакты и задачи выключены. Пользователь включает их вручную. Графики в первом выпуске экрана доступны переключателем и не обязательны: при выключенных графиках отчёт остаётся полным.

Текущий отчёт чек-листов остаётся отдельным документом и отдельной кнопкой. «Сводный отчёт», если в нём включены чек-листы, читает тот же снимок и не пишет в пакеты. Второй разбор формул не копировать.

Если для пресета «План/факт» нет ни денежных данных, ни дат, неактивная серая кнопка не показывается. Рядом со списком пресетов — короткое объяснение, какие данные нужно заполнить.

### 4.1. Снимок строго read-only

Новый `ProjectReportSnapshot` только читает уже загруженные массивы и `ChecklistReportSnapshotBuilder`. Он не вызывает `save`, `*ProgressStore.load`, `ChecklistPackStore.save` и `ChecklistWorkingNote.write`.

Проверка `ChecklistReportSnapshotBuilder` на коммите `9bc0097`:

- Перед чтением пакета `classify` смотрит файл или ключ UserDefaults через `fileExists` и `Data(contentsOf:)`. Каталоги и шаблонные пункты не создаются.
- Отсутствующий файл классифицируется как читаемый пустой пакет. Затем вызывается `ChecklistPackStore.load`. Его `decodeFile` при отсутствии файла возвращает `[]` и тоже ничего не создаёт. Это текущий контракт: нет файла — «не начат» / нет данных, а не ошибка и не повод создать JSON.
- Битый файл `classify` помечает как `.unreadable` и `load` не вызывает. В снимок попадает «Данные пакета не прочитаны.» Файл не переписывается и не подменяется шаблоном. Прямой `ChecklistPackStore.load` на битых байтах вернул бы `[]` и скрыл бы ошибку; новый снимок так делать не должен.
- Заметки читаются через `ChecklistWorkingNote.readDisplayText`. Запись и создание `BCNotes` есть только в `write`, билдер его не вызывает.
- `photoFileExists` проверяет путь и не создаёт каталоги.
- Методы `GeologyProgressStore.load` и остальные `*ProgressStore.load`, которые создают каталог или подмешивают шаблон, билдер не вызывает.

Новый снимок сохраняет этот контракт. Отсутствие файла не создаёт файл. Битый файл даёт понятную ошибку формирования и не исправляется.

## 5. Единый печатный стиль

Новые документы. Старые генераторы этим стилем не перекрашивать до миграции.

- Формат A4: 595.2 × 841.8 pt.
- Поля 40 pt. Снизу резерв 36 pt под колонтитул, сверху со второй страницы 48 pt под бегущую строку.
- Сетка: одна колонка текста. Таблица — фиксированные доли ширины, сумма 100%. Сумма всегда в правой колонке, выравнивание по правому краю, цифры моноширинные.
- Типографика, фиксированные размеры, не Dynamic Type: название документа 18 pt semibold, имя проекта 14 pt semibold, раздел 13 pt semibold, текст 10.5 pt, таблица 9.5 pt, колонтитул 8.5 pt. Межстрочный интервал 1.25.
- Шрифт с кириллицей: Arial / Arial Bold, как в отчёте чек-листов, запасной — системный.
- Титул: «BuildChecklists», название документа, имя проекта, адрес, ответственный, даты проекта если заданы, дата и время формирования, одна строка «Состояние на момент формирования».
- Колонтитул каждой страницы: слева дата формирования, справа «Стр. N». Со второй страницы сверху имя проекта, обрезанное с многоточием, не посреди слова, если есть место для целого слова.
- Палитра печатная и светлая независимо от темы: фон страницы белый, текст `white 0.12`, вторичный `white 0.38`, линейки `white 0.82`. Не использовать `UIColor.label`.
- Чёрно-белая читаемость: статус и знак отклонения дублируются словом («Выполнено», «Проблема», «Не выполнено», «Перерасход», «Экономия»). Цвет только усиливает слово.
- Даты новых PDF: `dd.MM.yyyy`, дата формирования ещё и `HH:mm`. Локаль — `Locale(identifier: Locale.preferredLanguages.first ?? Locale.current.identifier)`, то же правило, что у `ProjectDashboardView.dateString`. `ru_RU` не зашивать. Формат существующего отчёта чек-листов не менять.
- Деньги новых PDF: группировка разрядов, два знака после запятой, включая нулевые копейки, суффикс «₽». Ноль — «0,00 ₽». Отрицательную разницу план/факт показывать со знаком и словом. Старые PDF до миграции остаются без копеек.
- Длинное название и комментарий переносятся по словам внутри своей ячейки. Ячейка растёт по высоте. Строка таблицы не режется между страницами. Если строка выше остатка страницы, она начинается на следующей. Если строка выше целой страницы, она продолжается со следующей страницы с повтором заголовков колонок и пометкой «продолжение».
- Заголовок раздела и первая строка его таблицы не разрываются. Заголовок группы расходов не остаётся последней строкой страницы.
- На новой странице таблица повторяет заголовок колонок.
- Пустая секция не печатается. Исключение — весь документ без данных: одна фраза, почему отчёт пуст, без пустых таблиц.
- Графики не декоративные. Только четыре, и каждый скрывается по правилу ниже.

### 5.1. Графики

Все графики — простые столбцы или одна горизонтальная полоса на категорию. Подпись значения числом рядом со столбцом, чтобы чёрно-белая копия читалась без цвета. Не использовать круговые диаграммы, 3D и оси без подписей.

| График | Показывать | Скрывать |
| --- | --- | --- |
| План/факт бюджета | Одновременно есть этап с планом > 0 и этап с фактом > 0. Столбцы только у этапов, где план > 0 или факт > 0 | Есть только план, или только факт, или нет ни того ни другого. Только план — таблица без графика |
| Структура расходов | Минимум две категории с суммой > 0. Допустим, когда факта есть, а плана нет | Нет расходов или ровно одна ненулевая категория: таблица без графика |
| Прогресс по этапам | Хотя бы один пакет с `itemCount > 0` | Все пакеты пустые или непрочитанные. Непрочитанный пакет в график не ставить, он остаётся строкой текста |
| Отклонение сроков | Хотя бы два этапа `project.stages` с `plannedEnd` и (`actualEnd` или статус просрочки) | Меньше двух таких этапов. Один этап печатается строкой, не графиком |

Графики делаются отдельным этапом 6, после проверенных таблиц. Первый пользовательский выпуск экрана идёт после этапа 6, поэтому переключатель графиков уже есть. При выключенном переключателе каждый отчёт остаётся полноценным: таблицы и текст не зависят от рисунка.

График занимает не больше трети страницы и не рвётся. Под ним таблица с теми же числами. График без таблицы не публикуется.

## 6. Экран настройки

Новый экран `ReportExportView`. Старые «PDF проекта», «PDF чек-листов», «PDF (все)», «PDF для заказчика» и CSV остаются.

Первая точка входа — восьмое быстрое действие «Отчёты» на дашборде. Оно открывает `ReportExportView`. Действия «PDF проекта» и «PDF чек-листов» не меняются. Сетка по-прежнему считает колонки через `ProjectQuickActionMetrics.columns(for:)` от ширины контейнера и Dynamic Type: обычный текст даёт 3, 4 или 7 колонок, XXXL — 1, 2 или 4, крупные размеры доступности — 1, 2 или 3. Восьмое действие занимает следующую строку, если в текущей строке не хватает места. Короткая последняя строка остаётся по центру, как сейчас. Модель устройства и `UIScreen.main.bounds` не использовать. Проверка сетки: 320, 390 и 430 pt, iPad, Split View и Dynamic Type.

Пресеты:

- «Сводный отчёт» — владелец;
- «Для заказчика»;
- «Только чек-листы» — текущий полный отчёт или только замечания, не второй рендерер;
- «Только расходы»;
- «План/факт» — только если есть деньги или даты из раздела 3. Иначе кнопки нет. Рядом со списком — короткое объяснение, что заполнить. Серой неработающей кнопки нет.

Поля:

- аудитория задаётся пресетом. Заказчик не может включить внутренние пункты, замечания по пунктам, комментарии платежей, фото, задачи, телефоны и причины просрочки. Проценты пакетов, факт просрочки и даты остаются;
- период расходов: выключен, «от», «до» или оба. Независимые границы, перестановка если «от» позже «до». В новом отчёте граница «по» включает выбранный календарный день целиком. Старый заказчицкий PDF до миграции не менять; это временное различие записано в разделе 10;
- этапы нового экрана: все или выбранные `GlobalStageCategory`. Фильтр применяется только к новым документам. Пикеры этапа и типа в старом `ExpensesExportView` к старому генератору не подключать. Этапы таймлайна `project.stages` этим списком не фильтровать: ключа нет;
- включаемые блоки: чек-листы, расходы, замечания, задачи, контакты, комментарии, графики. Контакты и задачи у владельца по умолчанию выключены;
- оценка состава до генерации: число пакетов с данными, число замечаний, число операций после фильтра, есть ли план, есть ли даты. Оценка только читает. Не вызывает `*ProgressStore.load`;
- кнопка «Сформировать». Пустой результат не открывает Share Sheet.

Фильтры текущего экрана бюджета не меняются. «PDF (все)» по-прежнему игнорирует фильтры списка. «PDF для заказчика» на бюджете по-прежнему получает только период тумблера.

Share Sheet: один якорь popover, как `checklistReportConfigurePopover`. На iPhone — лист снизу. На iPad — popover от кнопки «Отправить». Не использовать `UIScreen.main.bounds` и модель устройства.

Файл нового отчёта — временный, с уникальным именем, не совпадающим со старыми `Expenses-*.pdf` и `BC_Report_*.pdf`. В Documents и в JSON проекта не писать. Пока файл открыт в preview или Share Sheet, его не удалять. Удаление — после закрытия просмотра и листа, по тому же правилу, что у `ChecklistReportExportView` (`shareOpen` не даёт стереть файл, пока лист держит URL).

- Битый пакет не исправляется.
- CSV-колонки.
- Демо-данные не становятся постоянными.
- Формат дат существующего PDF чек-листов (`ru_RU`, `dd.MM.yyyy HH:mm`).
- Старая граница «по» у `exportCustomerExpensesPDF`: сырое сравнение `Date`, без расширения до конца дня. Новые документы включают выбранный день целиком. Это различие держится до этапа 9 и снимается только вместе с удалением старого метода.

Новые файлы отчётов именуются отдельно, во временном каталоге, и не перезаписывают старые имена. Иначе новый рендерер затрёт файл, который ещё открыт старым ShareLink. Файл не удаляется, пока открыт preview или Share Sheet.

## 11. Рекомендуемый порядок

1. Этапы 1–2: основа и read-only снимок, без кнопки.
2. Этапы 3–4: «Сводный отчёт», заказчик, расходы. Таблицы без графиков уже полны.
3. Этап 5: две таблицы план/факт.
4. Этап 6: графики. До него экран пользователю не показывать.
5. Этап 7: `ReportExportView` и восьмое действие «Отчёты».
6. Этап 8: сравнение глазами со старыми PDF.
7. Этап 9: сначала переключение точек входа, затем отдельный коммит удаления недостижимых методов.

Чек-листы в этот порядок не встраивать как переписывание. Их кнопка и рендерер остаются. «Сводный отчёт» только читает их снимок.

## 12. Утверждённые решения

Утверждены 25 сентября 2026. Это больше не список вопросов.

1. Переходное расхождение источников согласовано. «Сводный отчёт» читает рабочие пакеты чек-листов. Старая кнопка «PDF проекта» до отдельной миграции читает `project.stages`. В интерфейсе новый документ называется «Сводный отчёт», чтобы его не принимали за тот же файл.
2. План/факт — две независимые таблицы. Деньги по `GlobalStageCategory`. Сроки по `project.stages`. Строки по названиям не объединять. Ключи в модели не добавлять.
3. График «План/факт бюджета» только при одновременном наличии плана и факта. Если есть только факт, график структуры расходов допустим при минимум двух ненулевых категориях. Одна категория — таблица без графика. Если есть только план — таблица без графика.
4. Пресет заказчика включает проценты чек-листов и краткий прогресс по пакетам. Не включает внутренние пункты, замечания по пунктам, комментарии платежей, фото, задачи, телефоны и причины просрочки. Факт просрочки и даты можно показывать без внутренней причины.
5. Контакты и задачи в пресете владельца по умолчанию выключены. Пользователь включает их вручную.
6. Первая точка входа — восьмое быстрое действие «Отчёты» на дашборде. Оно открывает `ReportExportView`. «PDF проекта» и «PDF чек-листов» не меняются. Сетка адаптируется по ширине контейнера, Dynamic Type и iPad теми же правилами `ProjectQuickActionMetrics`. Модель устройства и `UIScreen.main.bounds` не использовать. Проверить 320, 390, 430 pt, iPad, Split View и Dynamic Type.
7. В новом отчёте граница «по» включает выбранный календарный день целиком. Старый заказчицкий PDF до миграции не менять. Различие записано в разделе 10.
8. Пикеры этапа и типа в старом `ExpensesExportView` к старому генератору не подключать. Новый экран применяет свои фильтры только к новым документам.
9. Новые финансовые PDF показывают суммы с `₽` и двумя знаками после запятой, включая нулевые копейки. Старые PDF до миграции не менять.
10. Графики — отдельный этап 6 после проверенных таблиц. Первый пользовательский выпуск экрана выполняется после этапа 6, поэтому переключатель графиков уже есть. При выключенных графиках отчёт остаётся полноценным.
11. Даты новых PDF используют предпочитаемый язык системы, как `ProjectDashboardView.dateString`. `ru_RU` не зашивать. Формат существующего отчёта чек-листов не менять.
12. Старые методы удалять только в этапе 9: сначала переключить подтверждённые точки входа, затем повторно найти ссылки, затем удалить только недостижимые методы отдельным коммитом. CSV и рендерер чек-листов сохраняются. `projectPDFPath` и `pdfPaths` не затрагиваются.

Дополнительно утверждено:

- недоступный пресет «План/факт» не показывается серой кнопкой; рядом со списком — короткое объяснение, какие данные заполнить;
- новый снимок строго read-only;
- `ChecklistReportSnapshotBuilder` не вызывает `*ProgressStore.load` и не создаёт каталоги или шаблоны; отсутствующий файл пакета означает «не начат» и не создаёт файл; битый файл даёт ошибку чтения и не исправляется;
- временный PDF не удалять, пока его используют Share Sheet или preview.
