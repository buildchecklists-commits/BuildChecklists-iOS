# Стратегия переноса на Android

**Источник истины — iOS-проект в этой папке (релиз 1.0.3 / Build 9).**  
Android повторяет **пользовательское поведение**, а не обязан копировать файловую структуру Swift.

Архитектура Android может быть другой (ViewModel, Room, DataStore).  
Продуктовая логика должна быть идентичной: те же роли, лимиты, DEMO, этапы, статусы, план/факт.

Старые iOS-папки BuildChecklists 2 и 3 для сверки не использовать.

---

## Главное правило

```
iOS поведение  =  контракт продукта
Android код    =  реализация контракта
```

Если Android «удобнее» сделать иначе внутри — можно.  
Если из-за этого на экране другой %, другой DEMO или другой лимит USER — нельзя.

Сверка всегда против работающего iOS, не против воспоминаний и не против черновиков.

---

## Что должно совпасть один в один

### Доступ

- DEMO только по кнопке, не переживает процесс.
- Регистрация локальная по смыслу (на Android свой аналог профиля). После регистрации без подписки — только просмотр.
- USER: не больше 2 проектов.
- PRO: без лимита проектов.
- Нет активной подписки: данные видны, запись запрещена, путь в paywall.
- Restore покупок есть.
- Удаление аккаунта стирает локальные данные приложения.

Billing на Android — Google Play. Product ID будут другими, **матрица прав** — как в `SUBSCRIPTIONS.md`.

### Объект

- Поля: имя, адрес, даты, общий бюджет, прораб, описание, типы конструкций, цвет карточки, контакты, файлы.
- Типы фундамента / стен / перекрытий / формы крыши / покрытия — те же кейсы и русские названия, что в `Models/Enums.swift`.
- 11 рабочих стадий дашборда в том же порядке, что в `ProjectDashboardView`.

### Чек-листы

- Состав пунктов = JSON-паки iOS (`Resources/Seeds/*Packs`).
- Статусы пункта: ОК / Проблема / Н/Д. В прогресс идёт только ОК.
- «Инфо» по slug из тех же текстов (`Resources/InfoTexts`).
- Фото пункта принадлежит пункту, не только галерее проекта.
- Смена типа конструкции подгружает другой пак; прогресс старого типа не должен тихо приписываться новому без явного решения (на iOS файл store один на projectID — это известная хрупкость, на Android лучше сразу ключ `(projectId, typeId)`, но **видимый** UX сверить с iOS).

### Сроки

- Плановые и фактические даты на глобальных этапах проекта.
- Причины просрочки: погода, рабочие, материалы, заказчик, документы/сети, планирование, другое.
- Статусы этапа считаются как в `Stage.status` (факт важнее плана, затем календарь).

### Деньги

- Расход: сумма, дата, категория этапа, подкатегория (материалы / работа / аренда), комментарий.
- План: общий бюджет + план по стадиям.
- Факт: сумма расходов.
- DEMO-набор расходов и плановых сумм — как в `AppStore` префилле, если DEMO на Android делается.

### DEMO

Если DEMO переносится, он должен:

- создаваться той же кнопкой на приветствии;
- показывать тот же учебный объект (имя, адрес, типы, бюджет 12 000 000);
- иметь ненулевой прогресс геологии/фундамента/стен/перекрытий;
- иметь демо-фото и набор расходов;
- не подменять боевые данные пользователя после закрытия приложения;
- иметь сессионные подсказки на Проектах, Сроках, Бюджете, Фото, Профиле.

Не копировать баг неполной зачистки ProgressStore, если Android пишет DEMO на диск. На Android правильнее изолировать DEMO целиком в памяти или в отдельном namespace, **сохранив внешнее поведение** «после kill учебного проекта нет».

## Где Android может отличаться

| iOS | Android может |
|---|---|
| Один `AppStore` на всё | Несколько ViewModel + единый фасад доступа |
| JSON файлы + куча ProgressStore | Одна БД (Room) с таблицами project / stage_progress / expense / task |
| Merge по title | Стабильные id пунктов в паках + миграции |
| NotificationCenter для % | Flow/LiveData из репозитория прогресса |
| Двери и кровля в UserDefaults | Тот же репозиторий, что остальные стадии |
| `overallProgress` без дверей | **Пока копировать как на iOS**, пока на iOS не исправят формулу. Расхождение % — расхождение продукта |
| StoreKit 2 | Play Billing, те же тиры USER/PRO |
| SwiftUI TabView | Нижняя навигация с теми же пятью вкладками |

Улучшать внутренности можно. Молча «чинить» продукт на Android, не починив iOS, нельзя: тогда платформы разъедутся.

## Рекомендуемый порядок переноса

1. Каркас: онбординг, Welcome, табы, тема, локальный профиль.
2. Модель проекта + список + создание + лимит USER (пока заглушка биллинга).
3. Дашборд и 11 стадий: паки JSON перенести как ассеты 1:1.
4. Прогресс + фото пункта + «Инфо».
5. Сроки и причины просрочки.
6. Расходы, графики, экспорт.
7. Бюджет план/факт.
8. Задачи и уведомления.
9. Подписки Play Billing по матрице iOS.
10. DEMO и «Что нового».
11. Удаление аккаунта / wipe.
12. Поэкранная сверка с iOS 1.0.3.

Не начинать с калькуляторов и косметики. Сначала объект, чек-листы, деньги, доступ.

## Источники при сомнении

Смотреть в iOS:

1. `Store/AppStore.swift` — доменные правила.
2. `Store/SubscriptionService.swift` — матрица доступа.
3. `Views/Projects/ProjectDashboardView.swift` — состав стадий.
4. `Resources/Seeds/` — состав чек-листов.
5. `Docs/DEMO_MODE.md`, `Docs/SUBSCRIPTIONS.md`, `Docs/DATA_FLOW.md`.

Если iOS и черновик Android расходятся — побеждает iOS, пока отдельно не решено изменить продукт на обеих платформах.

---

## Критерий готовности экрана на Android

Экран готов, когда человек, знающий iOS, проходит тот же сценарий и не видит другого результата:

- те же поля и статусы;
- тот же смысл процентов;
- те же ограничения подписки;
- те же последствия DEMO после перезапуска.

Пиксель-перфект не требуется. Совпадение логики — обязательно.
