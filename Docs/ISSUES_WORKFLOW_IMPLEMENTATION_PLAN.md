Целевой цикл:

1. Открыть рабочий чек-лист этапа.
2. Поставить пункту статус «Проблема».
3. Увидеть, что пункт требует внимания.
4. Увидеть число активных замечаний.
5. Открыть единый список по проекту.
6. Перейти к этапу и пункту.
7. Снять/сменить статус того же пункта, без новой сущности.

## 1. Текущее состояние реализации

### 1.1. `ItemStatus`

Файл: `Models/Enums.swift`.

```swift
enum ItemStatus: String, Codable, CaseIterable, Identifiable {
    case ok, issue, na
    // title: «ОК» / «Проблема» / «Н/Д»
}
```

- `rawValue`: `"ok"`, `"issue"`, `"na"`. Менять нельзя.
- Уже Codable. JSONDecoder поднимает `"issue"` без миграции.
- `StorageService` для таймлайна тоже читает `dict["status"] as? String` через `ItemStatus(rawValue:)`. Неизвестная строка → `nil`, не краш.

### 1.2. Модель рабочего пункта

Файл: `Models/StageItem.swift`.

| Поле | Тип | Роль для замечаний |
| --- | --- | --- |
| `id` | `UUID` | Идентификатор пункта, `Identifiable` |
| `code` | `String` | Код из JSON-пака; merge **не** использует |
| `title` | `String` | Текст пункта; **ключ merge** в ProgressStore |
| `note` | `String?` | Поле модели; рабочий UI его **не** пишет |
| `status` | `ItemStatus?` | Нужное поле. Optional. |
| `severity` | `Severity?` | В рабочем UI не показывается |
| `photoPaths` | `[String]` | В ProgressStore сохраняется |
| `pdfPaths` | `[String]` | Есть в модели |
| `infoSlug` | `String?` | Справка; merge обновляет со шаблона |

Этап: `Models/Stage.swift` — `id: UUID`, `title: String`, `items: [StageItem]`. Статус этапа (`StageStatus`) считается **по датам**, не по чек-листу. `Stage.progress` считает только `status == .ok`.

### 1.3. Два контура (критично не смешать)

| Контур | Где живёт | Кто меняет `status` | Рабочий UI 1.0.3 |
| --- | --- | --- | --- |
| Таймлайн | `Project.stages` в JSON проектов | `AppStore.setStatus` → `mutate(...)` | **Не используется** для галочек |
| Рабочие чек-листы | `*ProgressStore` по `projectID` | Binding в `StageDetailView2` → `ProgressStore.save` | **Да** |

`AppStore.setStatus(projectID:stageID:itemID:status:)` пишет в **таймлайн**. Его вызывает только `ItemCardView`.

`ItemCardView` встроен в `StageDetailView`. Вызовов `StageDetailView(` в проекте **нет**. Это мёртвый путь. Три чипа «ОК / Проблема / Н/Д» в продакшен-UI **недоступны**.

Цикл замечаний должен писать **только ProgressStore**, тем же механизмом, что сегодняшняя галочка.

### 1.4. Рабочая строка: `ChecklistItemRow2`

Файл: `Components/ChecklistItemRow2.swift`.

Короткий тап по кружку:

```swift
item.status = (item.status == .ok) ? .na : .ok
```

Следствия:

- `issue` коротким тапом **не ставится**.
- Если в JSON уже `issue`, кружок рисуется как пустой (`checked = status == .ok`), заголовок не зачёркнут (зачёркивание только для `.ok`).
- Повторный тап превратит `issue` в `.ok` — пользователь не поймёт, что «проблема» исчезла. Это текущий дефект скрытого статуса, его нужно закрыть в UX (раздел 4).

Цвета сейчас: зелёный `checkmark.circle.fill` для ok, серый `circle` иначе. Отдельного цвета для issue нет.

Accessibility: у строки **нет** `accessibilityLabel` / `accessibilityIdentifier`. В приложении labels есть точечно (калькулятор, задачи, «Информация» в мёртвом `ItemCardView`).

Read-only: `store.isReadOnlyMode` → `disabled` + opacity 0.35. Это существующий замок подписки. **Не расширять и не дублировать paywall.**

Заметки рабочего пути: файлы `Documents/BCNotes/<item.uuid>.txt`, не `StageItem.note`. Список замечаний **не должен** читать `item.note` как источник правды.

### 1.5. Экран этапа: `StageDetailView2`

Файл: `Views/Stages/StageDetailView2.swift`.

- Binding на `Stage`, не на AppStore.
- Список: `ForEach(stage.items.indices, id: \.self)` — идентичность **по индексу**, не по `item.id`.
- Сохранение: `.onChange(of: stage)` и `.onDisappear` → `onStageChanged()` + `Notification.Name.bcProgressDidChange`.
- Прогресс шапки: только `.ok / count`.
- Меню (факт 1.0.3): «Отметить все пункты как выполненные» в `markAllItemsDone()` ставит **каждому** пункту `.ok`. «Сбросить прогресс этапа» в `resetStageProgress()` ставит **каждому** `.na`. Оба пути сейчас молча затирают `issue`. После появления UI замечаний это недопустимо. Безопасное поведение — раздел 4.9; меняется только локальная логика `StageDetailView2`, без модели и без AppStore.
- Paywall-sheet уже есть рядом с баннером «только просмотр». Новую логику подписок не добавлять.

Хабы паков (`GeologyStagesScreen`, `FoundationStagesScreen`, … `DoorsStagesScreen`, `LandscapingStagesScreen`):

- `NavigationLink` → `StageDetailView2`.
- `@State stages` грузится из ProgressStore (где есть merge — `load(projectID:typeID)`).
- `onChange(of: stages)` → `save` + нотификация.
- `ForEach(..., id: \.offset)` — тоже индекс.

`DoorsProgressStore` и `RoofCoverProgressStore` хранят JSON в **UserDefaults**, не в `BC_*`. Merge по шаблону у дверей и покрытия **нет**.

### 1.6. ProgressStore — как сохраняется статус

Типичный JSON-файл (пример фундамента): `Documents/BC_Foundation/<projectID>.json` — массив `Stage`, внутри `StageItem.status`.

`JSONEncoder`/`JSONDecoder` стандартные. Значение `"issue"` уже валидно.

Простой `load(projectID:)` — то, что читают список проектов и дашборд для %.  
`load(projectID:typeID:)` — merge шаблона с диском **по `title` этапа и `title` пункта**. UUID сохранённого пункта **сохраняется**, если title совпал.

При merge:

- новый пункт шаблона получает **новый** `UUID()` из `SeedPackLoader.loadSinglePack` (генерируется в момент загрузки пака);
- пункт, пропавший из шаблона, **не удаляется** — дописывается в конец;
- `infoSlug` обновляется со шаблона, статус/фото пользователя остаются на `existing`.

### 1.7. Дашборд и навигация

`ProjectDashboardView`:

- Открывается из `ProjectsListView` через `NavigationLink { ProjectDashboardView(projectID:) }` внутри `NavigationStack`.
- Секция «Чек-листы проекта»: 11 `NavigationLink` на хабы паков (геология … благоустройство).
- Прогресс пака: `*ProgressStore.load(projectID:)` (без merge).
- **Двери не входят** в `overallProgress` (и список проектов, и дашборд). Покрытие крыши входит.
- Нотификация `bcProgressDidChange` увеличивает `progressVersion` и перерисовывает %.
- Программируемого `NavigationPath` / deep link к пункту **нет**.
- Счётчика замечаний нет.

Вкладка «Сроки» (`MainTabView`) считает `AppStore.projectProgress` по **таймлайну** `Project.stages`, не по ProgressStore. Замечания рабочих чек-листов на эту формулу не влияют.

### 1.8. Идентификаторы

| Объект | ID | Стабильность |
| --- | --- | --- |
| Проект | `Project.id` | Стабилен |
| Пак / модуль | Нет enum в коде; 11 хардкод-строк на дашборде | Стабилен как набор экранов |
| Блок этапа в паке | `Stage.id` UUID, после первого save на диске | Стабилен, пока merge нашёл этап по **title** |
| Пункт | `StageItem.id` UUID | Стабилен при совпадении **title**; иначе новый UUID |

Однозначно найти пункт по UUID можно **внутри текущего сохранённого ProgressStore**. Это не глобальный ID на всю жизнь пака: смена конструктива или переименование title в JSON-паке разрывает связь (см. риски).

### 1.9. Прогресс

Везде в рабочих экранах и на карточке проекта:

```text
percent = done / total
```

`issue`, `na` и `nil` **не** считаются выполненными. Проблемный пункт — невыполненный. Формулу в этой функции менять нельзя.

Фильтры есть у проектов, расходов, задач, фото. На `StageDetailView2` фильтров нет. Фильтр «Только проблемы» **подтверждённо не входит** в первую реализацию (раздел 8, часть 6).

Адаптив почти не используется (исключение — колонки бюджета). Дашборд и чек-листы — один `NavigationStack`, push. Отдельный iPad-сценарий не проектировать: тот же стек, те же списки.

### 1.12. Подписки и DEMO (только факты, без изменений)

- Подписка: `isReadOnlyMode` уже блокирует строку и экран этапа. Просмотр списка замечаний должен оставаться возможным, как просмотр чек-листа. Новых проверок тарифа, лимита USER, StoreKit, restore — не добавлять.
- DEMO: `setStageItemsStatus(..., .started)` ставит `.issue` **первому пункту таймлайна** `Project.stages`, не ProgressStore.
- Prefill ProgressStore в DEMO: `applyAllOK` / `applyPartialOK` — только `.ok` и `.na`. В рабочих чек-листах DEMO замечаний **нет**, пока пользователь их не поставит.
- DEMO пишет ProgressStore на диск (существующее поведение). Если пользователь в DEMO поставит issue, файл появится. **Prefill и вход в DEMO не менять.** Не добавлять замечания в сид.

| Сохраняется ли `issue` без смены схемы? | Да. Поле `StageItem.status` уже `ItemStatus?`, enum уже содержит `issue`. ProgressStore кодирует весь `Stage`. |
| Может ли старый проект 1.0.3 содержать `issue`? | В **рабочем** ProgressStore — редко: UI 1.0.3 пишет только ok/na. В таймлайне DEMO — да, но это другой контур. ## 2.1. Как не перепутать два механизма хранения статусов

В коде одновременно живут два независимых `status` у структур с похожими именами.

| | Рабочий чек-лист (нужен) | Таймлайн (не трогать) |
| --- | --- | --- |
| Экран | `StageDetailView2` + `ChecklistItemRow2` | `StageDetailView` + `ItemCardView` (нет вызовов) |
| Binding | `$stage.items[j].status` | `AppStore.setStatus` |
| Сохранение | `*ProgressStore.save(projectID:stages:)` | `StorageService` / JSON проектов, поле `Project.stages` |
| Поиск этапа | `Stage.id` внутри файла/UserDefaults пака | `stageID` внутри `Project.stages` |
| Файлы | `BC_*` и ключи дверей/кровли | файл проектов |

Правила реализации (чек-лист для ревью):

1. Не вызывать `AppStore.setStatus`, `setNote`, `addPhoto` с `projectID/stageID/itemID` для этой функции.
2. Не импортировать и не встраивать `ItemCardView` / `StageDetailView`.
3. Не читать `project.stages` в collector и не фильтровать таймлайн по `.issue`.
4. Collector вызывает только `*.load(projectID:)` у ProgressStore, включая `DoorsProgressStore` и `RoofCoverProgressStore`.
5. Host перехода загружает тот же простой `load(projectID:)`, что и collector — **без** `load(projectID:typeID:)` merge. Иначе открытие замечания может перезаписать файл шаблоном.
6. Сохранение host — тот же `save`, что у соответствующего `*StagesScreen`.
7. Если в diff реализации появился `Store/AppStore.swift` — это ошибка, кроме случайного несвязанного шума (его быть не должно).

DEMO-префилл кладёт `.issue` в **таймлайн**. Список замечаний этого не покажет. Не «чинить» префилл.

## 3. Пользовательский сценарий

Сценарий для обычного проекта с активной подпиской (не DEMO-специфичный).

1. Пользователь открывает объект → дашборд.
2. Видит строку **«Замечания»** и число активных (двери входят в число). Если 0 — строка есть, подпись «Нет».
3. Открывает пак → блок → рабочий список `StageDetailView2`.
4. Свайп или долгое нажатие → **«Отметить как проблему»**. Короткий тап по кружку не назначает `issue`.
5. Строка: оранжевый индикатор, заголовок не зачёркнут.
6. Счётчик на дашборде обновляется по `bcProgressDidChange`.
7. Список замечаний показывает все активные `issue` по 11 ProgressStore, включая двери.
8. Тап открывает **тот же** `StageDetailView2` нужного блока, минуя хаб пака. Прокрутка — по возможности, иначе видимо название пункта в этом блоке.
9. Закрытие только явными командами: **«Проблема устранена»** → `ok`, **«Снять отметку проблемы»** → `na`. Короткий тап на `issue` статус не меняет.
10. Пункт исчезает из списка. Тот же UUID, без новой сущности.

Read-only: просмотр списка и переход разрешены; назначение/снятие блокирует существующий `isReadOnlyMode`.  
DEMO: тот же UI, префилл не менять.

## 4. Предлагаемый интерфейс

Не копировать PWA. Стиль iOS: `dashboardGlass`, `dashboardRow`, `NavigationLink`, insetGrouped, `AccentYellow`.

### 4.1. Окончательные названия команд

Проверено на соответствие текущей логике статусов: `ok` = выполнено (входит в %), `na` = не выполнено / снято (не входит в %), `issue` = проблема (не входит в %). Короткий тап сегодня переводит только `ok` ↔ `na`. Поэтому закрытие замечания без приёмки должно давать `na`, а закрытие с приёмкой — `ok`.

| Команда | Когда видна | Действие | Почему так |
| --- | --- | --- | --- |
| **Отметить как проблему** | статус не `issue` | → `issue` | Явно, совпадает с `ItemStatus.title` «Проблема» |
| **Проблема устранена** | статус `issue` | → `ok` | Пункт принят, замечание закрыто, % вырастет |
| **Снять отметку проблемы** | статус `issue` | → `na` | Замечание снято, пункт снова не выполнен — как после снятия галочки |

Не использовать короткие «Снять отметку» и «Снять проблему»: первое путается со снятием галочки «выполнено», второе не говорит, будет ли пункт принят.

Без confirmation при `ok` → `issue`: жест уже явный (свайп или меню), не короткий тап.

### 4.2. Жесты

| Жест | Поведение |
| --- | --- |
| Короткий тап, `na` | → `ok` (как 1.0.3) |
| Короткий тап, `ok` | → `na` (как 1.0.3) |
| Короткий тап, `issue` | **Не менять статус.** Haptic. VoiceOver: «Пункт отмечен как проблема. Закройте замечание из меню или свайпом.» |
| Свайп trailing, не issue | «Отметить как проблему» |
| Свайп trailing, issue | «Проблема устранена» (основное) и при необходимости второе действие «Снять отметку проблемы». Если два trailing неудобны — оба в context menu, в свайпе только «Проблема устранена». Предпочтение: оба действия в **context menu**; в свайпе при `issue` — «Проблема устранена», при не-issue — «Отметить как проблему». «Снять отметку проблемы» всегда доступна из долгого нажатия. |
| Context menu | Те же три команды по состоянию |
| Read-only | жесты disabled, как кружок сейчас |

Жесты вешать на строку в `StageDetailView2` (`swipeActions` / `contextMenu`) или на `ChecklistItemRow2`, если не ломает List. Не добавлять третий чип как в мёртвом `ItemCardView`.

### 4.3. Цвет, иконка, текст

| Статус | Кружок | Заголовок |
| --- | --- | --- |
| `na` | серый `circle` | primary |
| `ok` | зелёный `checkmark.circle.fill` | secondary + strikethrough |
| `issue` | оранжевый `exclamationmark.circle.fill` | primary, без зачёркивания |

Слово в UI: **«Проблема»**, не «Нужно внимание». `Severity` в v1 не показывать.

### 4.4. Счётчик и список

Дашборд, строка над «Чек-листы проекта»: «Замечания», число в Capsule (оранжевый если > 0, иначе «Нет»). Subtitle при N>0: «Требуют внимания». Двери входят в N. Формулу % на шапке не подписывать и не менять.

Список — push как расходы. Строка: иконка, `item.title`, subtitle `«Пак · Блок»`, иконка фото при непустых `photoPaths`. Секции по паку в порядке дашборда. Empty:

```
Замечаний нет
Отметьте пункт как «Проблема» в чек-листе этапа.
```

Свайп в **списке замечаний** статус не меняет — только в рабочем чек-листе.

### 4.5. Подсветка найденного пункта

При успехе: фон строки `Color.orange.opacity(0.18)` на 1–1,5 с.  
При неуспехе прокрутки: тот же блок открыт, сверху временное сообщение с названием пункта (раздел 6).

### 4.6. iPhone и iPad

Один NavigationStack, без split, без `NavigationPath` корня приложения.

### 4.7. VoiceOver и identifiers

### 4.8. Сообщение, если пункт не найден

**Заголовок:** Пункт не найден

**Кнопка:** Закрыть

### 4.9. Массовые действия — зафиксированное безопасное поведение

Факт кода (`StageDetailView2`):

```swift
func markAllItemsDone() {
    for idx in stage.items.indices {
        stage.items[idx].status = .ok   // затирает issue
    }
}
func resetStageProgress() {
    for idx in stage.items.indices {
        stage.items[idx].status = .na   // затирает issue
    }
}
```

Алерты уже локальные (`showMarkAllDoneConfirm`, `showResetProgressConfirm`). Модель не нужна: цикл по `stage.items`, запись того же `status`.

Это **можно и нужно** сделать локально, без архитектуры и без AppStore.

#### «Отметить все пункты как выполненные»

1. Подтверждение. Если есть замечания, в тексте: «Пункты без замечаний будут отмечены как выполненные. Замечания не изменятся.»
2. Пункты с `status == .issue` **не перезаписывать**.
3. Остальные → `.ok`.
4. После: alert  
   **Отмечено выполненными: N. Замечания сохранены: M.**  
   N = число пунктов **без** `issue` в этом блоке (все они после действия имеют `ok`).  
   M = число пунктов с `issue` (не изменялись).
5. Кнопка «Отметить» не должна быть `.destructive`, если замечания сохраняются (сейчас в 1.0.3 она destructive — поменять роль на обычную).

#### «Сбросить прогресс этапа»

- Если M == 0: текущий диалог «Сбросить прогресс этапа?» / Отмена / Сбросить. Все → `na`.
- Если M > 0: **отдельное** подтверждение.  
  **Заголовок:** Сбросить прогресс этапа?  
  **Текст:** Будут сняты все отметки этого блока, включая \(M) замечаний. Это нельзя отменить.  
  **Отмена** — ничего не менять.  
  **Сбросить всё** (destructive) — все пункты, **включая** `issue`, → `na`.
- Пока пользователь не подтвердил — диск не писать.

«Удалить все фото этапа» статусов не трогает — оставить как есть.

## 6. Навигация к пункту и прокрутка

Подтверждено: из списка → существующий `StageDetailView2` нужного блока, хаб пака не показывать. `?highlight=` и корневой `NavigationPath` — нет.

Координаты перехода (только память): `projectID` + in-memory pack + `stageID` + `itemID`.

Host (`IssueStageDetailHost`): простой load → найти `Stage` где `id == stageID` **и** пункт `id == itemID`. Если нет — alert из 4.8, экран блока не открывать, статус на диске не трогать.

Если найдено: Binding в `StageDetailView2`, save как у хаба этого пака. Назад — в список замечаний.

### Сравнение двух способов прокрутки

**Вариант A.** Сменить основной `ForEach` на `id: \.id` (UUID пункта) и `scrollTo(itemID)`.

| Влияние | Оценка |
| --- | --- |
| Bindings `$stage.items[j]` | Нужно искать индекс по UUID на каждый кадр; ошибка индекса ломает запись |
| Обновление строк | SwiftUI пересоздаст identity всех строк один раз |
| Сохранение статуса | Само по себе не ломает, но сброс `@State` строки (bounce, picker) возможен |
| Анимации кружка | `@State checkBounce` привязан к identity строки → сбросится |
| Массовые действия | Идут по индексам массива — код жив, но List может анимировать «удаление/вставку» всех строк |
| Стабильность | Выше риск регрессии всего чек-листа ради прокрутки |

**Вариант B (выбран).** Оставить `ForEach(stage.items.indices, id: \.self)`. Искать индекс `j` где `stage.items[j].id == highlightItemID`. `ScrollViewReader.scrollTo(j)`. Подсветка по `@State highlightedItemID` / индексу, без смены identity.

| Влияние | Оценка |
| --- | --- |
| Bindings | Без изменений, тот же `$stage.items[j]` |
| Сохранение / массовые действия | Тот же цикл по индексам |
| Анимации | Identity прежняя |
| Прокрутка | `scrollTo` по id ForEach = индекс; в `List` на iOS 17 **не гарантирована** |
| Неверный пункт | Не открываем: сравнение строго UUID |

**Выбор: вариант B.** Прокрутка — nice-to-have. Целостность binding и массовых действий важнее. Масштабная замена ForEach на UUID в первой поставке запрещена.

Минимальный v1:

1. Открыть правильный блок.
2. Попытаться `scrollTo` индекс.
3. Если пункт на экране — подсветить.
4. Если прокрутка не сработала — не падать: показать название пункта над списком («Пункт: …») и оставить пользователя в верном блоке.

Не искать пункт в соседних блоках и не открывать «похожий» title.

Точный состав:

```text
struct ChecklistIssueRef: Identifiable {
```
