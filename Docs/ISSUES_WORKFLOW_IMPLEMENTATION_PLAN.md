## 1. Текущее состояние реализации

### 1.1. `ItemStatus`

Файл: `Models/Enums.swift`.

```swift
enum ItemStatus: String, Codable, CaseIterable, Identifiable {
    case ok, issue, na
    // title: «ОК» / «Проблема» / «Н/Д»
}
```

- `rawValue`: `"ok"`, `"issue"`, `"na"`. Менять нельзя.
- Уже Codable. JSONDecoder поднимает `"issue"` без миграции.
- `StorageService` для таймлайна тоже читает `dict["status"] as? String` через `ItemStatus(rawValue:)`. Неизвестная строка → `nil`, не краш.

### 1.2. Модель рабочего пункта

Файл: `Models/StageItem.swift`.

| Поле | Тип | Роль для замечаний |
| --- | --- | --- |
| `id` | `UUID` | Идентификатор пункта, `Identifiable` |
| `code` | `String` | Код из JSON-пака; merge **не** использует |
| `title` | `String` | Текст пункта; **ключ merge** в ProgressStore |
| `note` | `String?` | Поле модели; рабочий UI его **не** пишет |
| `status` | `ItemStatus?` | Нужное поле. Optional. |
| `severity` | `Severity?` | В рабочем UI не показывается |
| `photoPaths` | `[String]` | В ProgressStore сохраняется |
| `pdfPaths` | `[String]` | Есть в модели |
| `infoSlug` | `String?` | Справка; merge обновляет со шаблона |

Этап: `Models/Stage.swift` — `id: UUID`, `title: String`, `items: [StageItem]`. Статус этапа (`StageStatus`) считается **по датам**, не по чек-листу. `Stage.progress` считает только `status == .ok`.

### 1.3. Два контура (критично не смешать)

| Контур | Где живёт | Кто меняет `status` | Рабочий UI 1.0.3 |
| --- | --- | --- | --- |
| Таймлайн | `Project.stages` в JSON проектов | `AppStore.setStatus` → `mutate(...)` | **Не используется** для галочек |
| Рабочие чек-листы | `*ProgressStore` по `projectID` | Binding в `StageDetailView2` → `ProgressStore.save` | **Да** |

`AppStore.setStatus(projectID:stageID:itemID:status:)` пишет в **таймлайн**. Его вызывает только `ItemCardView`.

`ItemCardView` встроен в `StageDetailView`. Вызовов `StageDetailView(` в проекте **нет**. Это мёртвый путь. Три чипа «ОК / Проблема / Н/Д» в продакшен-UI **недоступны**.

Цикл замечаний должен писать **только ProgressStore**, тем же механизмом, что сегодняшняя галочка.

### 1.4. Рабочая строка: `ChecklistItemRow2`

Файл: `Components/ChecklistItemRow2.swift`.

Короткий тап по кружку:

```swift
item.status = (item.status == .ok) ? .na : .ok
```

Следствия:

- `issue` коротким тапом **не ставится**.
- Если в JSON уже `issue`, кружок рисуется как пустой (`checked = status == .ok`), заголовок не зачёркнут (зачёркивание только для `.ok`).
- Повторный тап превратит `issue` в `.ok` — пользователь не поймёт, что «проблема» исчезла. Это текущий дефект скрытого статуса, его нужно закрыть в UX (раздел 4).

Цвета сейчас: зелёный `checkmark.circle.fill` для ok, серый `circle` иначе. Отдельного цвета для issue нет.

Accessibility: у строки **нет** `accessibilityLabel` / `accessibilityIdentifier`. В приложении labels есть точечно (калькулятор, задачи, «Информация» в мёртвом `ItemCardView`).

Read-only: `store.isReadOnlyMode` → `disabled` + opacity 0.35. Это существующий замок подписки. **Не расширять и не дублировать paywall.**

Заметки рабочего пути: файлы `Documents/BCNotes/<item.uuid>.txt`, не `StageItem.note`. Список замечаний **не должен** читать `item.note` как источник правды.

### 1.5. Экран этапа: `StageDetailView2`

Файл: `Views/Stages/StageDetailView2.swift`.

- Binding на `Stage`, не на AppStore.
- Список: `ForEach(stage.items.indices, id: \.self)` — идентичность **по индексу**, не по `item.id`.
- Сохранение: `.onChange(of: stage)` и `.onDisappear` → `onStageChanged()` + `Notification.Name.bcProgressDidChange`.
- Прогресс шапки: только `.ok / count`.
- Меню (факт 1.0.3): «Отметить все пункты как выполненные» в `markAllItemsDone()` ставит **каждому** пункту `.ok`. «Сбросить прогресс этапа» в `resetStageProgress()` ставит **каждому** `.na`. Оба пути сейчас молча затирают `issue`. После появления UI замечаний это недопустимо. Безопасное поведение — раздел 4.9; меняется только локальная логика `StageDetailView2`, без модели и без AppStore.
- Paywall-sheet уже есть рядом с баннером «только просмотр». Новую логику подписок не добавлять.

Хабы паков (`GeologyStagesScreen`, `FoundationStagesScreen`, … `DoorsStagesScreen`, `LandscapingStagesScreen`):

- `NavigationLink` → `StageDetailView2`.
- `@State stages` грузится из ProgressStore (где есть merge — `load(projectID:typeID)`).
- `onChange(of: stages)` → `save` + нотификация.
- `ForEach(..., id: \.offset)` — тоже индекс.

`DoorsProgressStore` и `RoofCoverProgressStore` хранят JSON в **UserDefaults**, не в `BC_*`. Merge по шаблону у дверей и покрытия **нет**.

### 1.6. ProgressStore — как сохраняется статус

Типичный JSON-файл (пример фундамента): `Documents/BC_Foundation/<projectID>.json` — массив `Stage`, внутри `StageItem.status`.

`JSONEncoder`/`JSONDecoder` стандартные. Значение `"issue"` уже валидно.

Простой `load(projectID:)` — то, что читают список проектов и дашборд для %.  
`load(projectID:typeID:)` — merge шаблона с диском **по `title` этапа и `title` пункта**. UUID сохранённого пункта **сохраняется**, если title совпал.

При merge:

- новый пункт шаблона получает **новый** `UUID()` из `SeedPackLoader.loadSinglePack` (генерируется в момент загрузки пака);
- пункт, пропавший из шаблона, **не удаляется** — дописывается в конец;
- `infoSlug` обновляется со шаблона, статус/фото пользователя остаются на `existing`.

### 1.7. Дашборд и навигация

`ProjectDashboardView`:

- Открывается из `ProjectsListView` через `NavigationLink { ProjectDashboardView(projectID:) }` внутри `NavigationStack`.
- Секция «Чек-листы проекта»: 11 `NavigationLink` на хабы паков (геология … благоустройство).
- Прогресс пака: `*ProgressStore.load(projectID:)` (без merge).

- Счётчика замечаний нет.

Вкладка «Сроки» (`MainTabView`) считает `AppStore.projectProgress` по **таймлайну** `Project.stages`, не по ProgressStore. Замечания рабочих чек-листов на эту формулу не влияют.

| Объект | ID | Стабильность |
| --- | --- | --- |

## 2.1. Как не перепутать два механизма хранения статусов

В коде одновременно живут два независимых `status` у структур с похожими именами.

| | Рабочий чек-лист (нужен) | Таймлайн (не трогать) |
| --- | --- | --- |
| Экран | `StageDetailView2` + `ChecklistItemRow2` | `StageDetailView` + `ItemCardView` (нет вызовов) |
| Binding | `$stage.items[j].status` | `AppStore.setStatus` |
| Сохранение | `*ProgressStore.save(projectID:stages:)` | `StorageService` / JSON проектов, поле `Project.stages` |
| Поиск этапа | `Stage.id` внутри файла/UserDefaults пака | `stageID` внутри `Project.stages` |
| Файлы | `BC_*` и ключи дверей/кровли | файл проектов |

Правила реализации (чек-лист для ревью):

1. Не вызывать `AppStore.setStatus`, `setNote`, `addPhoto` с `projectID/stageID/itemID` для этой функции.
2. Не импортировать и не встраивать `ItemCardView` / `StageDetailView`.
3. Не читать `project.stages` в collector и не фильтровать таймлайн по `.issue`.
4. Collector вызывает только `*.load(projectID:)` у ProgressStore, включая `DoorsProgressStore` и `RoofCoverProgressStore`.
5. Host перехода загружает тот же простой `load(projectID:)`, что и collector — **без** `load(projectID:typeID:)` merge. Иначе открытие замечания может перезаписать файл шаблоном.
6. Сохранение host — тот же `save`, что у соответствующего `*StagesScreen`.
7. Если в diff реализации появился `Store/AppStore.swift` — это ошибка, кроме случайного несвязанного шума (его быть не должно).

DEMO-префилл кладёт `.issue` в **таймлайн**. Список замечаний этого не покажет. Не «чинить» префилл.

## 3. Пользовательский сценарий

Сценарий для обычного проекта с активной подпиской (не DEMO-специфичный).

1. Пользователь открывает объект → дашборд.
2. Видит строку **«Замечания»** и число активных (двери входят в число). Если 0 — строка есть, подпись «Нет».
3. Открывает пак → блок → рабочий список `StageDetailView2`.
4. Свайп или долгое нажатие → **«Отметить как проблему»**. Короткий тап по кружку не назначает `issue`.
5. Строка: оранжевый индикатор, заголовок не зачёркнут.
6. Счётчик на дашборде обновляется по `bcProgressDidChange`.
7. Список замечаний показывает все активные `issue` по 11 ProgressStore, включая двери.
8. Тап открывает **тот же** `StageDetailView2` нужного блока, минуя хаб пака. Прокрутка — по возможности, иначе видимо название пункта в этом блоке.
9. Закрытие только явными командами: **«Проблема устранена»** → `ok`, **«Снять отметку проблемы»** → `na`. Короткий тап на `issue` статус не меняет.
10. Пункт исчезает из списка. Тот же UUID, без новой сущности.

Read-only: просмотр списка и переход разрешены; назначение/снятие блокирует существующий `isReadOnlyMode`.

## 4. Предлагаемый интерфейс

Не копировать PWA. Стиль iOS: `dashboardGlass`, `dashboardRow`, `NavigationLink`, insetGrouped, `AccentYellow`.

### 4.1. Окончательные названия команд

Проверено на соответствие текущей логике статусов: `ok` = выполнено (входит в %), `na` = не выполнено / снято (не входит в %), `issue` = проблема (не входит в %). Короткий тап сегодня переводит только `ok` ↔ `na`. Поэтому закрытие замечания без приёмки должно давать `na`, а закрытие с приёмкой — `ok`.

| Команда | Когда видна | Действие | Почему так |
| --- | --- | --- | --- |
| **Отметить как проблему** | статус не `issue` | → `issue` | Явно, совпадает с `ItemStatus.title` «Проблема» |
| **Проблема устранена** | статус `issue` | → `ok` | Пункт принят, замечание закрыто, % вырастет |
| **Снять отметку проблемы** | статус `issue` | → `na` | Замечание снято, пункт снова не выполнен — как после снятия галочки |

Не использовать короткие «Снять отметку» и «Снять проблему»: первое путается со снятием галочки «выполнено», второе не говорит, будет ли пункт принят.

Без confirmation при `ok` → `issue`: жест уже явный (свайп или меню), не короткий тап.

### 4.2. Жесты

| Жест | Поведение |
| --- | --- |
| Короткий тап, `na` | → `ok` (как 1.0.3) |
| Короткий тап, `ok` | → `na` (как 1.0.3) |
| Короткий тап, `issue` | **Не менять статус.** Haptic. VoiceOver: «Пункт отмечен как проблема. Закройте замечание из меню или свайпом.» |
| Свайп trailing, не issue | «Отметить как проблему» |
| Свайп trailing, issue | «Проблема устранена» (основное) и при необходимости второе действие «Снять отметку проблемы». Если два trailing неудобны — оба в context menu, в свайпе только «Проблема устранена». Предпочтение: оба действия в **context menu**; в свайпе при `issue` — «Проблема устранена», при не-issue — «Отметить как проблему». «Снять отметку проблемы» всегда доступна из долгого нажатия. |
| Context menu | Те же три команды по состоянию |
| Read-only | жесты disabled, как кружок сейчас |

Жесты вешать на строку в `StageDetailView2` (`swipeActions` / `contextMenu`) или на `ChecklistItemRow2`, если не ломает List. Не добавлять третий чип как в мёртвом `ItemCardView`.

### 4.3. Цвет, иконка, текст

| Статус | Кружок | Заголовок |
| --- | --- | --- |
| `na` | серый `circle` | primary |
| `ok` | зелёный `checkmark.circle.fill` | secondary + strikethrough |
| `issue` | оранжевый `exclamationmark.circle.fill` | primary, без зачёркивания |

Слово в UI: **«Проблема»**, не «Нужно внимание». `Severity` в v1 не показывать.

### 4.4. Счётчик и список

Дашборд, строка над «Чек-листы проекта»: «Замечания», число в Capsule (оранжевый если > 0, иначе «Нет»). Subtitle при N>0: «Требуют внимания». Двери входят в N. Формулу % на шапке не подписывать и не менять.

Список — push как расходы. Строка: иконка, `item.title`, subtitle `«Пак · Блок»`, иконка фото при непустых `photoPaths`. Секции по паку в порядке дашборда. Empty:

```
Замечаний нет
Отметьте пункт как «Проблема» в чек-листе этапа.
```

Свайп в **списке замечаний** статус не меняет — только в рабочем чек-листе.

### 4.5. Подсветка найденного пункта

При успехе: фон строки `Color.orange.opacity(0.18)` на 1–1,5 с.  
При неуспехе прокрутки: тот же блок открыт, сверху временное сообщение с названием пункта (раздел 6).

### 4.6. iPhone и iPad

Один NavigationStack, без split, без `NavigationPath` корня приложения.

### 4.7. VoiceOver и identifiers

### 4.9. Массовые действия — зафиксированное безопасное поведение

Факт кода (`StageDetailView2`):

```swift
func markAllItemsDone() {
    for idx in stage.items.indices {
        stage.items[idx].status = .ok   // затирает issue
    }
}
func resetStageProgress() {
    for idx in stage.items.indices {
        stage.items[idx].status = .na   // затирает issue
    }
}
```

Алерты уже локальные (`showMarkAllDoneConfirm`, `showResetProgressConfirm`). Модель не нужна: цикл по `stage.items`, запись того же `status`.

Это **можно и нужно** сделать локально, без архитектуры и без AppStore.

#### «Отметить все пункты как выполненные»

1. Подтверждение. Если есть замечания, в тексте: «Пункты без замечаний будут отмечены как выполненные. Замечания не изменятся.»
2. Пункты с `status == .issue` **не перезаписывать**.
3. Остальные → `.ok`.
4. После: alert  
   **Отмечено выполненными: N. Замечания сохранены: M.**  
   N = число пунктов **без** `issue` в этом блоке (все они после действия имеют `ok`).  
   M = число пунктов с `issue` (не изменялись).
5. Кнопка «Отметить» не должна быть `.destructive`, если замечания сохраняются (сейчас в 1.0.3 она destructive — поменять роль на обычную).

#### «Сбросить прогресс этапа»

- Если M == 0: текущий диалог «Сбросить прогресс этапа?» / Отмена / Сбросить. Все → `na`.
- Если M > 0: **отдельное** подтверждение.  
  **Заголовок:** Сбросить прогресс этапа?  
  **Текст:** Будут сняты все отметки этого блока, включая \(M) замечаний. Это нельзя отменить.  
  **Отмена** — ничего не менять.  
  **Сбросить всё** (destructive) — все пункты, **включая** `issue`, → `na`.
- Пока пользователь не подтвердил — диск не писать.

«Удалить все фото этапа» статусов не трогает — оставить как есть.

### 13.1. Часть 1 — существующий текст заметки

Модель рабочего пункта — тот же `StageItem` (`Models/StageItem.swift`) во всех 11 паках:

| Поле | Тип | Назначение | Где живёт в рабочем UI |
| --- | --- | --- | --- |
| `id` | `UUID` | Идентификатор пункта | JSON ProgressStore / UserDefaults |
| `code` | `String` | Код пака/типа | JSON |
| `title` | `String` | Название пункта чек-листа (шаблон) | JSON |
| `note` | `String?` | Текстовая заметка **в модели** | В рабочем пути **почти не используется** |
| `status` | `ItemStatus?` | `ok` / `issue` / `na` | JSON |
| `severity` | `Severity?` | Серьёзность (таймлайн) | JSON, рабочий UI не пишет |
| `photoPaths` | `[String]` | Абсолютные пути к фото | JSON |
| `pdfPaths` | `[String]` | Пути к PDF | JSON; рабочий UI не пишет |
| `infoSlug` | `String?` | Слаг справочного `.md`, не пользовательский текст | JSON, merge может обновить |

**Фактическое хранение рабочей заметки не в `StageItem.note`.**  
`ChecklistItemRow2` пишет UTF-8 файл:

`Documents/BCNotes/<itemUUID>.txt`

- Создание каталога при первом сохранении.
- Загрузка при открытии листа «Заметка».
- Сохранение по кнопке «Сохранить»; «Отмена» диск не трогает.
- Пустая строка всё равно создаёт файл; индикатор оранжевой точки смотрит на **наличие файла**, не на непустой текст.
- Поле `item.note` при этом **не заполняется**.

`AppStore.setNote` и `ItemCardView` пишут `StageItem.note` в **таймлайн** `Project.stages` / `projects.json`. Это другой контур. Список замечаний его не читает. `PDFReportService` тоже берёт `item.note` таймлайна, не `BCNotes`.

ProgressStore (9 файловых паков + двери/покрытие крыши в UserDefaults) сохраняет весь `StageItem` через `JSONEncoder`. Sidecar `BCNotes` в JSON **не попадает**, но файл остаётся на диске рядом с приложением.

Модель **одинакова** во всех 11 паках. Различается только место JSON: `BC_* / <projectID>.json` против `doors_progress_*` / `roofcover_progress_*`. UI строки — общий `ChecklistItemRow2`.

#### Можно ли использовать существующую заметку как описание проблемы?

**Да, как содержимое, без новой сущности и без миграции.** Это уже пользовательский текст, привязанный к тому же UUID пункта.

Ограничения:

1. Заметка **не привязана к статусу `issue`**. Пользователь может написать её при `ok`/`na` (напоминание, материал, комментарий прорабу). Если UI начнёт называть то же поле только «Описание проблемы», чужой смысл не сотрётся с диска, но **подпись станет ложной** для пунктов без замечания.
2. Перезапись: повторное «Сохранить» в редакторе **заменяет весь файл**. Нет версий. Расшифровка «в заметку» без явного правила append **уничтожит** предыдущий текст.
3. Смена статуса `issue` → `ok`/`na` **не удаляет** `BCNotes` и не чистит `item.note`.
4. Массовые действия: «Отметить все» и «Сброс» меняют только `status`. «Удалить все фото этапа» удаляет фото, **не заметки**. Отдельной массовой очистки заметок нет.
5. `ProjectIssuesCollector` читает JSON **без merge и без save**. Сейчас он **не читает** ни `BCNotes`, ни `item.note`. Добавить чтение файла `BCNotes/<itemID>.txt` можно только как `Data(contentsOf:)` / `String(contentsOf:)`, без записи. Это безопасно для 1.0.3.
6. Нестабильность UUID: merge паков сопоставляет пункты по `title` и **сохраняет `existing` целиком**, включая `id`. Файл заметки обычно переживает смену шаблона. Если title пункта в шаблоне переименуют, старый файл может стать сиротой. Навигация/collector по UUID это уже учитывают.

**Вывод части 1:** переиспользовать `BCNotes` как текст замечания можно **без миграции**. Не писать в `StageItem.note` «на всякий случай» — это другой контур и риск расхождения. Не считать `item.note` источником для списка рабочих замечаний: там пусто.

### 13.2. Часть 2 — существующие фотографии

Связь с пунктом: массив `StageItem.photoPaths`. Каждый элемент — **полный путь** (`…/Documents/BC_Media/Images/<UUID>.jpg`), который возвращает `MediaService.save(image:)`. Не относительный путь, не отдельная UUID-метамодель, не хеш.

Файлы:

- Каталог: `Documents/BC_Media/Images/`.
- Имя файла: новый `UUID.jpg`.
- Перед записью: длинная сторона > 2000 px уменьшается; JPEG `compressionQuality: 0.9`.
- Поиск: `existingFileURL` пробует абсолютный путь, затем `BC_Media/Images/<basename>`, затем старые `BCPhotos`.

В ProgressStore сохраняется **массив строк-путей**. Миниатюры на диск не пишутся.

Несколько фото: **да**. `PhotosPicker` до 12 за один заход; повторное добавление дописывает в массив. Жёсткого лимита на пункт нет.

Реализация **одна** для всех 11 паков (`ChecklistItemRow2` + Binding в ProgressStore). Таймлайн `AppStore.addPhoto` — другой контур, в список замечаний не входит.

Смена статуса фото **не удаляет**. «Отметить все» / «Сброс» фото не трогают. Явное удаление:

- контекстное меню одного кадра;
- «Удалить все фото» в галерее пункта;
- «Удалить все фото этапа» в `StageDetailView2` — файлы + `photoPaths.removeAll()`, статусы не меняет.

Collector уже берёт `photoCount: item.photoPaths.count` **без загрузки изображений и без записи**. Первую строку пути можно положить в in-memory `ChecklistIssueRef` так же. Считать «живые» файлы vs битые пути — только `FileManager.fileExists` / `existingFileURL`, без merge.

Отсутствующий файл: галерея пункта показывает плейсхолдер «Файл не найден»; `photoPaths` остаётся. Список, если начнёт грузить `UIImage(contentsOfFile:)`, получит nil — нужна заглушка, не удаление пути «за пользователя».

Память: JPEG до ~2000 px в каждой строке списка — **недопустимо**. Текущий список показывает только «Фото: N» — это правильно. Если миниатюра понадобится:

- не декодировать полный кадр в collector;
- не держать `[UIImage]` на все замечания;
- грузить уменьшенное изображение лениво в видимой строке (downsample) **или** отложить миниатюры до отдельного шага.

`deleteProject` удаляет фото **только из таймлайна** `Project.stages`. Файлы `BC_Media`, на которые ссылается ProgressStore, и JSON паков **не чистятся**. Это уже существующий пробел; голосовые файлы унаследуют его, если не расширять удаление проекта отдельно.

### 13.6. Предлагаемый UX vs архитектура

Полный сценарий «свайп → форма Новое замечание → обязательные фото/голос/текст → статус только после Save» **не соответствует** уже принятому и частично реализованному циклу:

- статус ставится сразу через Binding в ProgressStore;
- короткий тап не трогает `issue`;
- форма перед статусом ломает быстрый осмотр объекта;
- отмена формы vs уже записанный `issue` усложняет консистентность;
- навигация к пункту ещё не сделана, а форма «дополнить» без перехода к пункту всё равно потребует редактор.

**Рекомендуемый более простой UX первой версии (согласован с вариантом A):**

1. Жест «Отметить как проблему» **как сейчас** сразу ставит `issue` (свайп / меню). Без модалки.
2. Текст — существующая «Заметка» + системная диктовка. Не переименовывать глобально в «Описание проблемы», пока заметка живёт и у пунктов без `issue`. В списке замечаний показывать этот текст как описание, если он непустой.
3. Фото — существующая кнопка и галерея.
4. Список: название пункта, этап, пак, фрагмент заметки, «Фото: N». Без шеврона, без перехода (как в незакоммиченном коде).
5. Снятие `issue` не удаляет текст и фото.
6. Голос и Speech — следующие релизы (B, затем C), не в том же коммите, что список.

Поздняя форма «Дополнить замечание» возможна **после** перехода к пункту (часть 5 текущего плана) как обёртка над теми же note/photo/audio, не как отдельная сущность.

Сохранение только текста / только аудио / аудио+текст — продукт этапа B/C. На этапе A «только текст» и «только фото» уже возможны независимо.

### 13.10. Разделение на этапы

Нельзя безопасно выпустить A+B+C одним релизом: B требует микрофон и файловый контур, C — Speech, отказ в разрешении, on-device fallback, правки политики. Это другой тестовый объём и другой риск ревью App Store.

#### Вариант A — минимальный безопасный релиз (рекомендуется следующим шагом после коммита списка)

- Статус `issue` (уже есть).
- Существующая `BCNotes` как описание в списке (чтение collector, без записи, без переименования редактора у всех статусов).
- Существующие фото: счётчик уже есть; миниатюры не грузить.
- Системная диктовка: **ноль кода**.
- Форму «Новое замечание» и обязательность вложений **не делать**.
- Новых полей нет. Миграции нет. Разрешений нет.

#### Вариант B — голосовые заметки (отдельный релиз)

- `AVAudioRecorder` → `BCAudio/<itemUUID>.m4a`.
- Play/pause/удаление, лимит длительности, temp при отмене, прерывание сессии.
- Индикатор и длительность в списке (чтение файла, не JSON).
- `NSMicrophoneUsageDescription`.
- Не включать Speech.
- Custom `Codable` не нужен.
- Согласовать cleanup при удалении проекта (можно тем же релизом B или сразу после).

#### Вариант C — распознавание (после B)

- Только on-device Speech.
- Разрешение Speech; при отказе/недоступности — аудио сохраняется.
- Расшифровка редактируется, затем **append или замена `BCNotes` только после явного выбора пользователя**.
- Повторная расшифровка с того же файла.
- Обновить Privacy Policy.
- Сервер Apple Speech и сторонние API — нет.

### 13.12. Риски приватности

- Клавиатурная диктовка: обработка вне приложения; не логировать буфер.
- In-app запись: аудио на устройстве в Documents; попадёт в iCloud/iTunes backup.
- Speech on-device: не отправлять буфер сами.
- Speech через Apple servers: не использовать.
- Расшифровка в `BCNotes` — тот же уровень чувствительности, что у текущих заметок (нет шифрования).
- Политика: https://buildchecklists-commits.github.io/buildchecklists-privacy/ — править перед C, не перед A.

### 13.13. Размер данных и backup

- Заметки: килобайты.
- Фото: уже основной вес; ресайз 2000 px уже есть.
- Аудио 3 мин AAC моно — примерно единицы мегабайт на пункт; главный риск — много замечаний × длинные записи. Лимит длительности обязателен.

### 13.15. Нужны ли новые optional-поля?

Для A и B1 — **нет**. Существующих `status`, `photoPaths` и sidecar `BCNotes` (+ будущий `BCAudio`) достаточно.

Новое JSON-поле допустимо только с `decodeIfPresent` и безопасным default. Обязательное поле без значения для 1.0.3 — **запрещено**.

### 13.16. Риски совместимости с 1.0.3 (сводка)

1. Синтезированный `Codable` + новый ключ в `StageItem` → pack JSON не декодируется → collector/экраны пустые, прогресс «пропал» визуально.
2. Запись в `item.note` параллельно `BCNotes` → два источника правды.
3. Использование `pdfPaths` под аудио → порча смысла поля.
4. Автоудаление заметок/фото/аудио при смене статуса → потеря полевых данных.
5. Обязательная форма на жесте `issue` → старые пустые issue валидны, новые — нет; плюс регресс осмотра.
6. Загрузка всех JPEG в список → память.
7. Merge/save в collector при чтении заметок → пересохранение 1.0.3 (уже запрещено правилом collector).
8. Смена UUID пункта при смене типа конструкции → сирота `BCNotes`/`BCAudio` (уже известный риск, не новый формат).
9. `deleteProject` не чистит рабочие файлы — не регрессия A, но голос увеличит мусор.
10. Добавление mic/speech keys без UI — риск ревью, не данных.

### 13.17. Решение (стоп)

Следующий **код** по голосу/форме/Speech **не писать**. Сначала по команде пользователя: коммит уже готового счётчика и списка **без** расширения модели. Затем отдельно A (чтение заметок в список). B и C — следующие релизы.

Подписки и DEMO не затронуты. Незакоммиченные `ProjectDashboardView`, `ProjectIssuesListView`, collector, pbxproj **не откатывались**. Коммит этим разделом **не создаётся**.

## 14. Форма замечания: сохранение, отмена, навигация

Уточнённый сценарий (не этап B/C): «Отметить как проблему» открывает форму. Статус `issue` ставится только после успешного сохранения. Голос на этом этапе — системная диктовка клавиатуры. Аудиофайлы, Speech и новые разрешения не используются.

### 14.1. Временные фотографии

`PhotosPicker` в строке чек-листа сразу вызывает `MediaService.save`. Для формы это небезопасно при отмене.

В `IssueEditorView` выбранные изображения держатся в памяти (`IssueDraftPhoto.incoming`). На диск они попадают только в `IssueContentSaver.persist`. Отмена просто закрывает sheet: файлы не создаются.

Уже сохранённые `photoPaths` показываются как `.existing`. Удаление в форме убирает их из черновика; файлы на диске удаляются только после успешного persist и обновления `photoPaths`.

### 14.2. Порядок сохранения и откат

Не транзакция ФС. Минимизация частичного состояния:

1. Записать новые JPEG в `BC_Media/Images` (существующий `MediaService.save`).
2. Записать обрезанный текст в `BCNotes/<itemUUID>.txt` (тот же путь, что у `ChecklistItemRow2`). Если текста нет — удалить файл заметки, если он был, не создавать пустой.
3. При ошибке шага 1 или 2: удалить **только вновь созданные** JPEG из шага 1. Существующую заметку, существующие фото и `status` не трогать. Форма остаётся открытой.
4. Только после успеха 1–2: `item.photoPaths = kept + created`, затем `item.status = .issue`.
5. Binding этапа вызывает `onStageChanged` → `ChecklistPackStore.save` / штатный ProgressStore хаба.
6. Best-effort удалить файлы фото, которые пользователь убрал из черновика.
7. `bcProgressDidChange` — счётчик и список перечитывают ProgressStore и `BCNotes`.

`StageItem.note` не пишется. Новых полей нет.

Новое замечание требует непустой текст **или** хотя бы одну фотографию (уже существующую в черновике или новую). Старые `issue` без содержимого в списке остаются.

### 14.3. Навигация из списка

Без корневого `NavigationPath`. `ProjectIssuesListView` → локальный `NavigationLink` → `IssueStageDetailHost(projectID, pack, stageID, itemID)`.

Host: `ChecklistPackStore.load` без merge (как collector). Ищет `Stage.id == stageID` **и** пункт `id == itemID`. Если нет — экран «Пункт не найден», статус не удаляется.

Если найдено: `StageDetailView2` с Binding, save через `ChecklistPackStore.save`. ForEach по-прежнему индексный. `ScrollViewReader.scrollTo(index)`. Подсветка строки временная. Над списком — «Пункт: …», если прокрутка в `List` не сработает.
