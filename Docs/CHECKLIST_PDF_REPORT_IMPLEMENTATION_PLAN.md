## 1. Аудит существующего PDF-кода

В приложении три независимых генератора. Все используют `UIGraphicsPDFRenderer` (UIKit). `PDFKit` применяется только для просмотра уже готового файла, не для сборки страниц. HTML и WebView для PDF нет.

### 1.1. Отчёт проекта

`Services/PDFReportService.swift`, метод `makeProjectReport(project:stages:expenses:)`.

Запуск: кнопка дашборда «Экспорт отчёта в PDF» (`ProjectDashboardView.exportPDF`). Подпись кнопки обещает сводку по объекту, расходам и чек-листам. Подписки на кнопку нет.

Страница A4 595×842. Поля 32. Текст через `NSString.draw` и `boundingRect`, перенос по словам, шрифты 20 / 16 / 14 / 12. Цвет `.label` и `.secondaryLabel` — системные, зависят от темы. Кириллица рисуется системным шрифтом.

Содержимое:

1. «Отчёт по проекту», имя, адрес, даты начала и окончания, ответственный, дата генерации (`DateFormatter.dateStyle = .medium`).
2. «1. Чек-листы по этапам» — переданные `stages`: заголовок, subtitle, пункты со значками ✅ / ⚠️ / ◻️ и `item.note`.
3. «2. Расходы» — итог, суммы по категориям, детализация. Если расходов нет, раздел пропускается.

Нет фотографий, колонтитулов, номеров страниц, прогресса, пакетов и статусов словами. Блок, который выше одной страницы, начинается с новой страницы и всё равно рисуется целиком: длинная заметка может выйти за край.

Файл пишется в Documents: `BC_Report_<имя с заменой «/» на «_»>_<unix>.pdf`. Каталог не временный. Старые файлы не удаляются. В `projectPDFPath`, `pdfPaths` и JSON проекта путь не записывается.

После успеха URL кладётся в `reportURL` и открывается `Components/ShareSheet.swift` (`UIActivityViewController`). Ошибка только в `print`, без alert. У `ShareSheet` нет `popoverPresentationController`: на iPad системный share без якоря может не показаться. То же у `ExpensesShareSheet`.

### 1.2. PDF расходов

`Store/AppStore.swift`:

- `exportExpensesPDF(for:)` — список расходов;
- `exportCustomerExpensesPDF(for:dateFrom:dateTo:)` — сводка для заказчика;
- `exportExpensesCSV(for:)` — не PDF, тот же экран экспорта.

Экран: `Views/Expenses/ExpensesExportView.swift`. Источник — `ExpenseItem` проекта, не чек-листы. Страница 595.2×841.8. Заголовки на русском. Список расходов дополнительно рисует комментарий через `CTFramesetter`; у этого блока фиксированный сдвиг и нет нормального переноса на следующую страницу.

Имена во временной папке: `Expenses-<имя>.pdf` и `Expenses-Customer-<имя>.pdf`. Пробелы заменяются на `_`, `/` на `-`. Повторная запись затирает файл с тем же именем. Явной уборки других временных PDF нет. В проект файл не сохраняется.

### 1.3. Просмотр чужого PDF

`PDFKit.PDFView` в приватном `PDFKitContainer`:

- `ProjectFilesView` — тот же просмотр файла проекта.

`MediaService.save(pdfData:name:)` пишет в `Documents/BC_Media/PDF`. `AppStore.addPDF` кладёт путь в `StageItem.pdfPaths` таймлайна. К новому отчёту это не относится: отчёт не должен становиться вложением пункта.

### 1.5. Что переиспользовать и что не трогать

Переиспользовать как образец, не как общий сервис:

- размер A4 и пословный перенос из `PDFReportService.draw`;
- идею временного файла из расходов, но с более строгим именем и уборкой;
- `PhotoThumbnailLoader.makeImage` — уменьшение через ImageIO, поворот `kCGImageSourceCreateThumbnailWithTransform`, исходный файл не меняется;

- `ChecklistPack.allCases` и `ChecklistPack.title` — порядок и названия 11 паков;
- `ChecklistPackStore.load` — чтение без merge и без save;
- `ChecklistWorkingNote.readDisplayText` — текст `BCNotes` без записи;
- `ProjectIssuesCollector` не расширять. Он собирает только строки `.issue` и первое фото, этого мало для полного отчёта.

Не менять:

- `PDFReportService` и кнопку «Экспорт отчёта в PDF»;
- `exportExpensesPDF`, `exportCustomerExpensesPDF`, `ExpensesExportView`;
- `ShareSheet` и `ExpensesShareSheet`;
- `MediaService.save(pdfData:)` и `pdfPaths`;
- просмотр `projectPDFPath`.

`PDFKit` импортирован в `PDFReportService`, но для генерации не используется. Новый отчёт тоже рисовать через `UIGraphicsPDFRenderer`, не через HTML.

## 3. Почему текущий отчёт не является отчётом рабочих чек-листов

Дашборд «Чек-листы проекта» читает 11 хранилищ. Кнопка PDF читает `project.stages`.

Это второй, старый контур. Рабочие статусы `ok` / `issue` / `na`, текст `BCNotes` и фото замечаний живут в файлах `BC_*` и в UserDefaults дверей и покрытия. Смешивать их с `Project.stages` нельзя: у таймлайна другие пункты, другие заметки и другой прогресс (`AppStore.projectProgress` считает среднее по `project.stages`).

Пользователь, который отметил проблему в рабочем чек-листе, в текущем PDF её не увидит. Кнопку старого отчёта не переименовывать и не переключать на ProgressStore: это отдельный документ, его контракт не менять.

## 4. Read-only snapshot

Новый тип в памяти, например `ChecklistReportSnapshot`. Он не пишется в `Project`, JSON и ProgressStore.

Сбор только чтением:

- 9 файловых паков: `Documents/BC_<Pack>/<projectUUID>.json` — geology, foundation, walls, slab, roof, engineering, windows, finishing, landscaping;
- двери: UserDefaults `doors_progress_<uuid>`;
- покрытие: UserDefaults `roofcover_progress_<uuid>`.

Пути и ключи уже собраны в `ChecklistPackStore.load`. Этот метод не создаёт папки и не вызывает save. Его и вызывать.

Не вызывать `*ProgressStore.load` и `load(projectID:typeID:)`:

- `GeologyProgressStore.load` при наличии файла мержит шаблон в памяти и на любом вызове создаёт каталог `BC_Geology`;
- файловые store в `fileURL` тоже создают каталог при чтении;
- большинство store помечены `@MainActor`;
- merge добавил бы пункты шаблона, которых нет в сохранённом прогрессе.

Если файла или ключа нет — пак пустой, шаблон из бандла не подставлять и не сохранять. Иначе PDF создаст «незаполненный чек-лист» и при следующем открытии экрана это может разойтись с тем, что пользователь ещё не открывал.

`ChecklistPackStore.load` при битом JSON возвращает `[]`, как при отсутствии файла. Этап 1 в `ChecklistReportSnapshot` отличает состояния без записи: файла или ключа нет; байты декодируются как `[Stage]`; байты есть, но не читаются. Пункты успешного пака берутся из `ChecklistPackStore.load`. Классификация только читает те же пути и ключи и не создаёт каталоги. Файл не чинится и не пересохраняется. Текст ошибки для PDF: «Данные пакета не прочитаны.» Путь к файлу в него не входит.

Порядок паков — `ChecklistPack.allCases`: geology, foundation, walls, slab, roof, roofCover, engineering, windows, doors, finishing, landscaping. Внутри пака сохранить порядок этапов и пунктов как в JSON.

Заметки: для каждого пункта снимка читать `ChecklistWorkingNote.readDisplayText`. Метод не создаёт `BCNotes`. Пустой и не-UTF-8 файл дают `nil`, пак при этом остаётся. `StageItem.note` в снимок не копировать. Раздел замечаний PDF по-прежнему показывает этот текст у статуса `issue`.

`ProjectIssuesCollector.issues` можно оставить для списка на дашборде. Для PDF он недостаточен: нет остальных статусов, нет всех `photoPaths`, нет прогресса. Коллектор не раздувать.

Снимок держит копии строк и путей, не открытые изображения. Картинки читаются позже, по одной, на этапе рисования.

Поля проекта для титула брать из уже загруженного `Project`: имя, адрес, ответственный, даты, описание, бюджет, `foundationType`, `wallType`, `slabType`, `roofShapeType`, `roofCoverType` через существующие `title`. Это не статусы чек-листов.

## 5. Структура PDF

Светлая страница: перед текстом заливка белым, текст чёрный и тёмно-серый. Не использовать `UIColor.label`. Поля около 32 pt, снизу резерв под колонтитул. Шрифты фиксированные: заголовок 20, раздел 16, подзаголовок 14, текст 12, колонтитул 10. Dynamic Type на PDF не действует.

### Титул

- BuildChecklists;
- название проекта;
- адрес, если не пустой;
- ответственный;
- дата и время формирования (`dd.MM.yyyy HH:mm`, локаль пользователя);
- общий прогресс одной цифрой, формула ниже;
- параметры дома, только если значение задано: фундамент, стены, перекрытия, форма крыши, покрытие;
- даты начала и планового окончания и бюджет, если заданы.

### Сводка

По всем успешно прочитанным пакам, включая двери:

- всего пунктов;
- выполнено (`ok`);
- замечаний (`issue`);
- не выполнено (`na` и отсутствующий статус);
- число этапов;
- число фотографий у пунктов со статусом `issue`.

Пакет, который не прочитался, в эти суммы не входит и перечисляется отдельно: «Не прочитан: Фундамент».

### Пакеты и этапы

Для каждого пака: название и прогресс пака. Если сохранённых данных нет — одна строка «Чек-лист ещё не заполнен», без пунктов шаблона. Если данные есть — этапы, прогресс этапа, пункты и словесный статус.

В общем списке проблемный пункт остаётся одной строкой статуса. Длинное описание и фотографии туда не копировать.

Если этап не влезает, на новой странице повторить название пака и этапа и пометку «продолжение». Строку пункта не резать посередине глифа. Заметка длиннее страницы режется по словам на несколько страниц, без обрезки.

Пустой раздел не печатать заглушкой «нет элементов» внутри заполненного пака, если массив пунктов реально пуст — достаточно строки этапа «Нет пунктов».

### Замечания

Отдельный раздел после всех паков. Тот же пункт уже был в общем списке со статусом «Проблема»; здесь только разбор: пакет, этап, название, текст `BCNotes` или «Описание не добавлено», фотографии или «Фотографий нет», счётчик вставленных и пропущенных кадров.

Режим «Только замечания» пропускает пошаговый список пунктов, но оставляет титул, сводку и этот раздел. Если замечаний нет — явная фраза «Замечаний нет», а не пустая страница.

### Завершение

В колонтитуле каждой страницы: «Состояние проекта на момент формирования», дата и время, «Стр. N». Полное «N из M» в первой версии не обязательно: для него нужен второй проход. Номер страницы без общего числа уже отличает страницы.

## 6. Статусы и прогресс

`rawValue` и `ItemStatus.title` не менять. В PDF свои подписи, потому что текущие подписи расходятся:

| Статус | `ItemStatus.title` | VoiceOver рабочего пункта | В PDF |
| --- | --- | --- | --- |
| `ok` | ОК | Выполнено | Выполнено |
| `issue` | Проблема | Проблема | Проблема |
| `na` | Н/Д | Не выполнено | Не выполнено |
| `nil` | — | как `na` в строке пункта | Не выполнено |

Комментарий у `na` говорит «не применяется / нет данных» и «0% прогресса». В рабочем списке это исходное состояние: серый кружок, тап переключает `na` ↔ `ok`, в процентах `na` не выполнен. Для отчёта верная пользовательская подпись — «Не выполнено», не «Н/Д» и не «не применяется».

Процент, как на экранах этапов и в строках дашборда:

`выполнено / все пункты`, где выполнено — только `status == .ok`.

`issue` и `na` в числитель не входят. Пустой этап — 0. Подпись процента как в экранах: `Int((value * 100).rounded()))%`.

Общий прогресс на карточке проекта и в списке проектов — среднее десяти чисел. Двери в это среднее не входят. Пустой пак даёт 0 и всё равно занимает одно из десяти мест. Делитель всегда 10.

PDF должен показать ту же цифру, посчитанную по снимку тех же десяти паков. Двери при этом есть в теле отчёта со своим процентом. В сводке рядом с общей цифрой короткая пометка, что она совпадает с карточкой проекта и не включает двери. Формулу в приложении в этом этапе не исправлять.

Прогресс пака и этапа в теле PDF — та же формула `ok / все пункты`, что у строки дашборда и `Stage.progress`. Здесь двери считаются как обычный пак.

Геология на дашборде может отличаться от файла: `GeologyProgressStore.load` подмешивает шаблон. PDF показывает только сохранённый JSON. Это осознанно: чтение отчёта не должно делать merge.

## 7. Заметки

Источник описания проблемы — только `BCNotes/<uuid пункта>.txt` через `readDisplayText`.

- нет файла, пустой файл, пробелы, не UTF-8 — в разделе замечаний «Описание не добавлено»;
- длинный текст переносится по словам и может занять несколько страниц;
- чтение не создаёт папку и не меняет файл;
- `StageItem.note` не печатать.

Заметку снимок читает у каждого пункта через `readDisplayText`. В разделе замечаний PDF печатать её у статуса `issue`. Пустой файл и не-UTF-8 дают отсутствие текста, без падения пака. `StageItem.note` не печатать.

## 8. Фотографии

Брать `photoPaths` только у пунктов `.issue`. Исходные JPEG не открывать целиком и не перезаписывать.

Для каждого пути: `PhotoThumbnailLoader.makeImage(path:maxPixelSize:)`. Ориентация уже учитывается флагом ImageIO. В PDF рисовать уменьшенный `UIImage` в прямоугольнике не шире колонки и не выше примерно 220 pt, с сохранением пропорций. После вставки отпускать изображение, не копить все кадры проекта в массиве.

Если `existingFileURL` не нашёл файл или ImageIO не собрал картинку — строка «Фото не удалось вставить» и имя не показывать пользователю как путь. Отчёт из-за одного кадра не отменять.

Лимит первой версии: не больше 8 фотографий на одно замечание, по порядку `photoPaths`. Остаток одной строкой: «Ещё N фото не включены». Файлы на диске не удалять. Лимит — константа рендерера, чтобы позже поднять её без смены модели.

Объём: текст по всем пакам небольшой, семена короткие. Размер PDF определяют фото. Восемь кадров на замечание при длинной стороне 1200 px остаются приемлемыми для share. Без лимита проект с десятками полноразмерных фото может раздуть файл и время.

## 10. Генерация и временные файлы

Этап 2: `ChecklistReportPDFRenderer` принимает готовый snapshot и URL назначения. Каталог и имя выбирает вызывающий код, не renderer. Сначала запись идёт во временный файл рядом с destination, затем он заменяет итоговый файл. При ошибке временный файл удаляется, уже существующий destination не затирается повреждённым PDF. В `projectPDFPath` и `pdfPaths` renderer ничего не пишет.

Каталог будущего UI: `FileManager.default.temporaryDirectory`, не Documents и не `BC_Media/PDF`.

Имя: `ChecklistReport-<безопасное имя>-<unix>.pdf`.

Очистка имени: убрать символы пути и недопустимые в имени (`/`, `\`, `:`, управляющие), схлопнуть пробелы, обрезать длину примерно до 40 символов. Пустое имя заменить на `Project`. Кириллицу в имени оставлять.

Перед записью удалить в временной папке только файлы с префиксом `ChecklistReport-`. Чужие `Expenses-*.pdf` и `BC_Report_*` не трогать.

Запись `.atomic`. Повторный экспорт создаёт новый timestamp и снова чистит префикс, поэтому старый временный отчёт не копится. Отмена удаляет недописанный файл этой попытки.

Нехватка места и прочие ошибки записи — наружу как ошибка, без записи в проект.

Успешный файл не добавлять в `projectPDFPath`, `documentPaths`, `pdfPaths` и не вызывать `persistProjects`.

## 11. UI, прогресс, просмотр, Share Sheet

На дашборде отдельная кнопка, не вместо старого экспорта. Например: «Отчёт по чек-листам», подпись «Текущее состояние рабочих чек-листов».

По нажатию — лист настроек с двумя переключателями и кнопкой «Сформировать». Пока идёт генерация, кнопка недоступна, виден индикатор. Отмена закрывает задачу.

Генерация в `Task.detached`: снимок, затем PDF. Прогресс и ошибки возвращать на главный поток. Глобальную очередь не заводить.

После успеха — share. Для iPad у нового `UIActivityViewController` задать `popoverPresentationController.sourceView` и `sourceRect` на контейнер листа, не меняя старый `ShareSheet`. На iPhone остаётся обычный sheet.

Отдельный экран PDFKit в первую версию не входит: просмотр даёт сам share sheet. Существующий приватный `PDFKitContainer` не вытаскивать и не обобщать.

Ошибка генерации — alert на листе настроек, share не открывать.

## 12. Ошибки

| Ситуация | Поведение |
| --- | --- |
| Нет ни одного сохранённого пака | PDF всё равно создаётся: титул и фраза «Рабочие чек-листы ещё не заполнены». Данные не создаются. |
| Один пак не читается | Остальные входят в отчёт. В сводке и на месте пака: «Данные пакета не прочитаны». Файл не чинить. |
| Повреждён JSON | То же, что нечитаемый пак. |
| Нет или битое фото | Строка в карточке замечания, отчёт продолжается. |
| Не удалось записать PDF | Alert «Не удалось создать PDF». |
| Нехватка места | Alert с текстом системной ошибки, без повтора записи в Documents. |
| Share не собрался | Alert «Не удалось открыть отправку». Файл проекта не менять. |
| Отмена | Задача отменена, частичный файл удалён, проект не изменён. |

Частичный отчёт при одном битом паке лучше, чем отказ всего документа. В титуле или сводке это видно, а не спрятано в консоли.

## 13. Производительность

Чтение 11 JSON и заметок дёшево относительно фото. Дорогая часть — ImageIO и запись страниц.

Снимок без изображений. Кадры по одному на фоне. Между паками и кадрами проверять `Task.isCancelled`.

Повторное нажатие блокируется флагом на время задачи. Индикатор без процентов в первой версии достаточен; дробный прогресс можно добавить счётчиком обработанных замечаний, если генерация заметно длиннее секунды.

UIKit-рисование PDF выполнять в той же фоновой задаче, не на главном потоке. На главный поток только URL, ошибка и признак «идёт генерация».

## 14. Accessibility

Лист настроек: подписи переключателей, `accessibilityIdentifier` в существующем стиле (`project.checklistReport.issuesOnly`, `project.checklistReport.includePhotos`, `project.checklistReport.generate`). Кнопка дашборда — отдельный identifier. Состояния «идёт формирование» и ошибка доступны VoiceOver. Dynamic Type на листе не обрезает подписи (`fixedSize` по вертикали, перенос).

В самом PDF размер шрифта не меньше 10 pt, контраст чёрный по белому, текст не обрезается многоточием.

## 15. Совместимость iOS 1.0.3

Функция только читает. Не меняет модели, JSON проекта, ProgressStore, UUID, статусы и не делает миграцию. Проект 1.0.3 не пересохраняется из-за экспорта.

Отсутствующие поля проекта уже декодируются как `nil` или `[]`. Пустой прогресс — нормальный отчёт «ещё не заполнен», а не повод создать файлы паков.

DEMO и подписки не ветвить и не менять. Чтение в DEMO допустимо, потому что save и `ensureCanMutate` не вызываются.

Старый PDF проекта и PDF расходов остаются на своих данных.
