# DEMO-режим

Сессионный учебный режим релиза **1.0.3 / Build 9**.  
Пользователь видит полноценный объект без покупки подписки. После закрытия приложения DEMO не восстанавливается.

---

## Вход

DEMO **не** включается на холодном старте. В `bootstrap()` явно:

```
isDemoMode = false
```

Включение только действием пользователя:

1. `WelcomeView` — кнопка «Попробовать демо» → `store.enterDemoMode()` и запрос уведомлений (`requestAuthorizationOnce`).
2. `LoginView.enterDemo()` — тот же вызов, но `LoginView` в навигации **нигде не создаётся**. Рабочий вход — Welcome.

Корневой экран пускает в `MainTabView`, если `isRegistered || isDemoMode`.

После входа показывается баннер DEMO на списке проектов и сессионные coachmark’и:

- Проекты (`ProjectsListView`)
- Сроки (`PlanProjectsListView` в `MainTabView`)
- Бюджет (`BudgetProjectsListView`)
- Фото (`GlobalPhotosView`)
- Профиль (`ProfilePlaceholderView`)

Coachmark’и живут только в `@State`. Повторно в той же сессии после закрытия не появляются. Между запусками не сохраняются.

Экран «Что нового» к DEMO не привязан: он завязан на версию приложения.

## Создание demo-данных

Всё делает `AppStore.enterDemoMode()` одним проходом.

1. `userRole = .demo`, `isDemoMode = true`, `isReadOnlyMode = false`.
2. Роль **не** пишется в UserDefaults (`persistUserRole` намеренно не вызывается).
3. Сбрасываются флаги «уже префиллили в этой сессии».
4. Если в UserDefaults есть `bc_last_demo_project_id` — удаляются артефакты прошлой сессии.
5. Массивы `projects / expenses / tasks` очищаются в памяти.
6. Последовательно:

| Шаг | Метод | Что делает |
|---|---|---|
| Проект | `createDemoProjectIfNeeded` | «Дом 160 м² (пример)», адрес в Наро-Фоминском г.о., прораб Олег, лента + газоблок + монолит + металлочерепица, бюджет 12 000 000 ₽ |
| Даты объекта | `applyDemoProjectDatesIfNeeded` | 01.02.2026 – 30.09.2026 |
| Таймлайн | `prefillDemoTimelineIfNeeded` | Геология закрыта в срок; фундамент закрыт с задержкой «Погода»; стены/перекрытия/крыша с планом; остальные без факта |
| План бюджета | `prefillDemoPlannedBudgetByStageIfNeeded` | Фиксированные суммы по `GlobalStageCategory` |
| Статусы `Project.stages` | `prefillDemoProgressIfNeeded` | Геология и фундамент все `ok`; стены ~60% `ok`; перекрытия первый пункт `issue` |
| ProgressStore | `prefillDemoProgressStoresIfNeeded` | Геология и фундамент 100%; стены ~55%; перекрытия ~32% |
| Фото | `prefillDemoPhotosIfNeeded` | Ассеты `foundation_demo_1`, `walls_demo_1`, `slab_demo_1` в первые пункты соответствующих store |
| Расходы | `prefillDemoExpensesIfNeeded` | Набор фактов по всем стадиям через `addExpense` |

Созданный UUID пишется в `bc_last_demo_project_id`.

Создание проекта и расходов идёт через штатные `createProject` / `addExpense`, поэтому модель совпадает с боевой. Persist JSON в DEMO пропускается.

## Ограничения и права

| Действие | В DEMO |
|---|---|
| Открыть приложение без профиля | Да |
| Редактировать чек-листы, сроки, расходы, задачи | Да (`canEditAnything == true`) |
| Лимит 2 проекта USER | Не действует |
| StoreKit / paywall как блокер записи | Не действует |
| Сохранить проекты/расходы/задачи в JSON | Нет (`persist*` сразу return) |
| Пережить перезапуск приложения | Нет: `bootstrap` снова выключает DEMO |
| Считаться зарегистрированным | Нет, пока пользователь не создаст профиль |

Профиль и DEMO ортогональны: регистрация выключает DEMO и грузит боевые данные с диска.

## Хранение

Заявленный контракт UI: «В демо-режиме данные не сохраняются после закрытия приложения».

Факт по коду:

| Данные | В DEMO |
|---|---|
| `projects.json` / `expenses.json` / `tasks.json` | Не пишутся |
| Роль `bc.user.role` | Не пишется как `demo` |
| `bc_last_demo_project_id` | Пишется |
| ProgressStore геологии/фундамента/стен/перекрытий | **Пишутся на диск** (префилл) |
| `BC_Media/Images` (демо-фото) | **Пишутся** через `MediaService` |
| Кровля / двери в UserDefaults | Могут появиться, если пользователь откроет эти стадии |
| Остальные `BC_*` | Могут появиться при работе пользователя в сессии |
| `BCNotes` | Могут появиться при заметках пунктов |

DEMO не изолирован полностью от файловой системы.

## Выход и очистка

`exitDemoMode()` вызывается из `register` и `login` (оба сначала ставят `isDemoMode = false`, поэтому выход нельзя завязывать на проверку этого флага внутри метода — код это учитывает).

Очистка:

1. `removeDemoProgressArtifacts` для всех `projects` в памяти и для UUID из UserDefaults.
2. Удаляется `bc_last_demo_project_id`.
3. `isDemoMode = false`.
4. Асинхронно: refresh StoreKit, применение роли, загрузка боевых JSON.

`removeDemoProgressArtifacts` удаляет только:

- `BC_Geology/{id}.json`
- `BC_Foundation/{id}.json`
- `BC_Walls/{id}.json`
- `BC_Slab/{id}.json`
- UserDefaults `roofcover_progress_{id}`
- UserDefaults `doors_progress_{id}`

Не удаляет: `BC_Roof`, `BC_Engineering`, `BC_Windows`, `BC_Finishing`, `BC_Landscaping`, `BC_Media`, `BCNotes`, `ProjectCovers`.

Logout и `deleteAccountAndWipeLocalData` DEMO отдельно не «выключают учебный контент»: logout чистит память и persist пустых массивов; wipe удаляет весь Documents.

## Известные проблемы

1. **Контракт «ничего не пишем на диск» нарушен.** Префилл ProgressStore и демо-фото сохраняются. После kill приложения DEMO-сессии нет, но файлы `{uuid}.json` и JPEG могут остаться до следующей попытки входа в DEMO (и то зачистка неполная).

2. **Неполная зачистка.** См. список папок выше. Если пользователь в DEMO открыл отделку или инженерию, файлы останутся.

3. **Два прогресса.** Префилл пишет и в `Project.stages`, и в ProgressStore. Карточка показывает ProgressStore. Таймлайн показывает даты `Project.stages`. Это намеренно разные картинки, но легко сломать, меняя только один префилл.

4. **Двери не входят в overallProgress.** Префилл дверей нет; даже если пользователь отметит двери, % на карточке не изменится.

5. **Демо-фото зависят от ассетов** `foundation_demo_1`, `walls_demo_1`, `slab_demo_1`. Если imageset пропадут, префилл фото тихо не выполнится (флаг сессии не поднимется, если ни одно фото не сохранилось).

6. **Таймлайн завязан на индекс этапов** (`stages[0]`, `[1]`, …), а статусы пунктов — на подстроку title («геология», «фундамент», «стен», «перекрыт»). Смена порядка или названий в `stages.json` сломает DEMO.

7. **`LoginView` мёртв.** Документировать его как пользовательский вход в DEMO нельзя.

8. **После DEMO пользователь без подписки попадает в read-only**, как только выйдет в профиль через регистрацию без покупки. Это ожидаемо, но резкий UX-переход.

9. **Уведомления.** Вход в DEMO запрашивает permission. Задачи в DEMO на диск не пишутся, но если пользователь создаст задачу с датой, notification может остаться в системе после выхода.

10. **Не создавать второй DEMO-проект «вручную» через createProject в той же сессии без анализа:** `createDemoProjectIfNeeded` срабатывает только при `projects.isEmpty`, но пользователь теоретически может создать ещё объекты — persist их всё равно не будет, а ProgressStore начнёт плодить файлы.

---

## Правила при изменении DEMO

- Менять тексты coachmark’ов можно локально в соответствующих View.
- Менять состав учебного объекта — только согласованно: проект, таймлайн, ProgressStore, расходы, план, фото, coachmark’и.
- Не включать `persistProjects` в DEMO «чтобы сохранить учебный прогресс».
- Расширяя зачистку, пройти все `BC_*`, медиа и UserDefaults кровли/дверей.
- Не включать DEMO автоматически в `bootstrap`.
